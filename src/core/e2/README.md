# Engine2 (`GN::e2`): World Runtime

This is the canonical approved design for the data-driven World Runtime. The
implementation assignment and historical verification records live in
[`agent/E2_WORLD_RUNTIME.txt`](../../../agent/E2_WORLD_RUNTIME.txt). The object-oriented runtime described below is implemented. The earlier
plain-value/schema-ID prototype has been replaced and the replacement has been
built and checked; see the validation section and active assignment for results.

SimpleWorld and mesh-viewer, including their dependent tests and samples, are
outside this refactor. Their separate removal work must not constrain this design.

## Object model

| Concept | Contract |
| --- | --- |
| Universe | Top-level lifetime context; may contain multiple Worlds. |
| World | Owns committed state, Law execution, Intent routing, ticks and publication. |
| Form | First-class individual: stable identity and Facet composition, without spatial hierarchy. FormId is its handle, not its entire object model. |
| Facet | Extensible capability object attached to a Form, with immutable configuration and application-facing methods. |
| FacetValue | Immutable per-version state object associated with a Facet, or world-level persistent state. |
| Mold | Creation recipe defining Facet composition and initial values. |
| Law | Coarse, cohesive domain of world evolution; may operate on many Forms. |
| Prime | Sole authoritative, persistent, committed world-state root. |
| PrimeView | Read-only view pinned to one complete published version. |
| Slate | Write-only set of proposed value and structural changes for a tick. |
| Intent | Directed operation request defined by its receiving Law. |
| Event | Observational output defined by its producing Law, for Presentation only. |
| Platform | Window, input, display and OS events, outside Simulation. |

Form, Law, Intent and Event derive from Being. Facet and FacetValue derive directly
from RuntimeType and RefCounter: they need runtime type information and reference
ownership, but no per-instance ID or name. All remain extensible classes using
the existing RuntimeType and Ref/AutoRef conventions. Applications
subclass them and expose their own typed methods. FormId remains a reference to a
Form; it does not replace the Form object. FormId is generated by its owning
Universe and is unique among Worlds in that Universe. Different Universes can
produce equal numeric IDs, so never transfer raw FormIds across Universes. Within
one Universe a target World rejects IDs that do not belong to it. Use
`RuntimeType::cast<T>()` and register
the direct parent class with `GN_REGISTER_RUNTIME_TYPE(...)`.

A Form composes actual Facet objects. A Facet can define a nested Value class
derived from FacetValue, along with related nested Intent classes. The Facet object
provides immutable configuration and a domain-specific interface, identified by
its owning Form and concrete type;
its Value supplies the state for a particular Prime version. Methods that read
state use an explicit PrimeView or a view-bound access contract. Methods requesting
changes send typed Intent objects. They do not mutate committed values or stash
causal state in the Facet itself.

Neither `Form::live()` nor `Facet::live()` drives world evolution. A view retains
its version through Form membership, Facet composition and Value access. Retaining
a stable object does not make it present in every version. Removing an object from
a later Prime must not invalidate its presence or state in an older retained view.

RuntimeType is the sole runtime type system. Do not add SchemaId, compiler-signature
hashes, canonical schema-name hashes, `void` payload storage or a parallel RTTI
registry. Registration and dispatch use existing RuntimeType identities; payloads
remain typed runtime objects behind their base-class references. Existing
RuntimeType linkage conventions apply across application/shared-library boundaries.
This does not introduce a serialization format or a cross-compiler plugin ABI.

Prime and its storage communicate with capabilities only through the common
Facet/FacetValue contracts: existing RuntimeType information and the applicable
virtual `clone()`, `valueType()`, `requirements()` and candidate `validate()` operations. Subclasses extend
or override that protocol without changing Prime. Core storage must not inspect
concrete Facet classes or domain fields. Typed accessors are client conveniences;
Laws and application code know concrete types, while Prime remains generic.

State belongs logically to its Facet, while private storage can group values by
runtime type for batch access. Prime is a version root, not necessarily a single
allocation. Shared unchanged Values and referenced resources remain immutable.
Object identity and configuration must not hide independently mutable causal
state. Public headers expose application extension contracts, not storage columns,
scheduler queues, candidate assembly or backend helpers.

## Prime, Slate and structural state

Prime contains Form existence, Facet composition, structural relationships, all
persistent FacetValue objects and necessary world-level state. Generation progress and
random-number state belong here because they affect future evolution. Laws may
retain algorithms and disposable caches; hidden mutable state must not become a
second authoritative store.

Every Law in tick N reads the same Prime[N]. Slate cannot be read as evolving
world state. Laws can copy inputs into local workspaces, calculate continuously,
and write final results. Later Laws cannot read earlier Laws' Slate outputs.
Same-tick requests and necessary computed parameters travel through Intents;
closely coupled calculations belong in one Law.

Slate exposes `set`, `setState`, `create`, `destroy`, `add` and `remove` operations.
It has no spatial reparent operation; changing a Transform parent is a typed Value
update by the appropriate Law.
A new FormId may be reserved and initialized inside Slate, but the Form is pending
until checkin. All Laws see stable Form membership and composition throughout a
tick. Initialization builds the first Prime before simulation starts; subsequent
world changes follow the same Slate/checkin path.

Each concrete Facet type has one registered owner Law for runtime value updates.
Ownership and Law-facing queries use exact concrete types. A base Facet and its
derived Facet may have separate owner Laws; registering a base writer does not
implicitly grant access to derived capabilities. Other Laws request changes via
the appropriate owner's Intents. Registration rejects duplicate ownership of the
same concrete type. Creation-time initialization and registered structural cleanup are
explicit, restricted exceptions: they cannot become arbitrary cross-Law writes.
Deleting a Form discards its pending value updates and removes it from the next
Prime. Structural operations validate against the candidate in recording order:
duplicate additions fail, removal of an absent registered Facet is a no-op, and
repeated owned value writes replace the earlier candidate value. Final composition
and domain invariants are checked before publication.

## Transform relationships and Facet requirements

Form has no parent/child relationship. Spatial hierarchy belongs entirely to
TransformFacet's versioned Value. A parent FormId of zero denotes a root; its pose
is world-space. A child stores its position and orientation relative to its parent's
Transform. Children are derived by querying Transform values for a matching parent,
not stored as a second list that can become inconsistent.

The public helpers are:

```cpp
struct WorldTransform {
    WorldVector3 position;
    Rotation orientation;
};
bool resolveWorldTransform(const PrimeView &, FormId, WorldTransform &);
DynaArray<FormId> transformChildren(const PrimeView &, FormId parent);
```

Resolution composes parent rotation and translation, with no inherited scale.
`transformChildren(view, 0)` returns roots; other IDs select direct children.
Both helpers operate on one PrimeView, including all ancestors. Retaining an old
view preserves its entire transform chain. Position composition preserves integer
world-coordinate precision. Core Prime/Form storage neither resolves transforms
nor knows what a TransformFacet is.

Changing the parent field is an ordinary Transform Value update. It keeps the
stored local position/orientation, so its world pose may change. A Law that wants
to preserve world pose computes the corresponding local pose explicitly before
writing. The engine does not impose a teleport, attachment or preserve-world policy.

Facet provides the generic virtual hook
`bool validate(const PrimeView &, FormId, const FacetValue &) const`, returning true
by default. It receives a read-only candidate PrimeView, the owning FormId and the
candidate Value. World invokes it during initialization and, after structural
changes and cleanup, before tick publication. Mold creation checks capability
requirements; world-dependent relationships are validated in the candidate World. The candidate
is available only to this validation phase, not as a second read source during Law
execution. Validation is pure: reject invalid state, do not mutate or run another
simulation stage.

TransformFacet uses the hook to require a parent Transform in the candidate World
and detect self-parenting/cycles in the final chain. Raw IDs carry no Universe tag;
callers must not transfer IDs between Universes, even when numerical values match.
Several coordinated Transform edits can therefore pass through intermediate
relationships that are incomplete, provided the final committed chain is valid.

`Slate::destroy(form)` deletes only that Form. Spatial parentage is not ownership
and never causes subtree deletion. Deleting a parent requires every surviving
child to be explicitly detached or reparented in the same tick; deleting the child
is also valid. Otherwise Transform validation rejects the candidate, preserving
the previous Prime and following the normal failure policy. The same applies to
removing a parent's Transform while children still reference it. The core must not
automatically detach children or choose replacement local poses.

Dynamics resolves all participant starting poses into a common world frame for
solving. Motion velocities remain world-space. It builds final solved world poses
and converts child outputs to local poses using each final parent transform before
writing Values; root outputs remain world-space. This avoids applying parent
movement twice or interpreting world-space solver outputs as local positions.

The local AABB solver requires resolved Body orientations to be identity (either
quaternion sign) and angular velocity to be zero. It explicitly rejects a static
Body under an ancestor with MotionFacet: compound bodies and kinematically attached
colliders are unsupported in this MVP. Generic Transform composition still supports
rotations; these restrictions belong to the demo DynamicsLaw, not World storage.

A Facet declares required types through `requirements() const`, returning
`DynaArray<const RuntimeType::TypeInfo *>` from existing RuntimeType identities. For example, MotionFacet requires TransformFacet. This is a composition
contract, not an instruction to construct missing objects or schedule another Law.
The World must validate actual final composition during initialization and before
checkin, including the requirements of every surviving Facet.

- Mold construction rejects Motion without Transform; initialization also validates
  composition before publishing the initial Form.
- Adding Motion and Transform in one structural batch is valid regardless of
  which addition is recorded first.
- Removing both in one batch is valid if no other surviving Facet requires them.
- Removing Transform while Motion survives is invalid.
- Missing requirements never trigger implicit Facet creation or default values.

Requirements are immutable capability metadata and are checked through existing
RTTI inheritance: a derived capability satisfies a base-type requirement. Multiple
matching derived siblings satisfy existence requirements. Lookup first prefers an
exact attached type; without an exact match, multiple derived matches make a
singular base-type lookup ambiguous and it returns no object. Law-facing queries
always select exact concrete Facet types; polymorphic explicit lookup does not
expand a Law's workload or write authority. No new type IDs or schema system is
needed. Deferred candidate validation lets a batch pass through incomplete
intermediate compositions without exposing them to readers. A failed final
validation leaves the previous Prime intact and follows the normal halt policy.

Subclassing a Facet extends its object interface, not its simulation semantics.
The application author must supply a compatible Law, by subclassing an existing
Law or implementing another one, and explicitly register the derived Facet's
concrete type in its contract. An existing DynamicsLaw is not required to handle
new derived Motion/Body capabilities automatically. A derived provider satisfying
a structural requirement likewise does not imply that an existing Law will query,
integrate or write it.

## Registration and extension

The application can register the following at any time during a running World:

1. Extensible Facet and corresponding FacetValue runtime types, initialization and
   safe immutable/versioned state behavior, and required Facet runtime types.
2. Molds composing actual Facet objects and initial Values.
3. Law objects, execution order and owned Facet/world-state types.
4. Each Law's accepted Intent classes and produced Event classes.
5. Restricted structural cleanup for references affected by removal, plus pure
   candidate validation through the common Facet virtual contract.

World has no seal operation or permanently frozen setup phase. Its live APIs are
`createForm(const Mold &)`,
`addFacet(FormId, const Facet &, const FacetValue &)`, `registerFacet`, `registerState`,
`addLaw` and `initializeState`. `addFacet` attaches a missing capability; it is not
an unrestricted replacement or write API for existing Values. `initializeState`
initializes missing world-level state and cannot replace existing persistent state.
Existing-state evolution still belongs to owner Laws through Slate.

Before the first tick, bootstrap creation/attachment/state initialization builds
Prime[0], validating each resulting composition before publication. After ticking
starts, these external structural/state additions are queued. The next tick latches
a stable batch and publishes accepted changes with its successful candidate. New
arrivals while a tick executes wait for the following tick. Returned pending FormIds
can be used for queued attachments, but do not make the Form visible in Prime yet.

Registration and Law additions remain allowed. Each executing tick retains a stable
registry and Law list; live additions become eligible at a subsequent tick boundary,
never halfway through a Law sequence. Register types before creating a World Form from a Mold, attaching a capability,
initializing state or adding an owner/receiver contract. Duplicate types, owners,
receivers or already-present attachments remain errors; openness does not relax
these invariants.

All Laws still read the tick-start Prime. A new Form, Facet or state item staged
for publication in this tick is first available to simulation in the following
tick. Bootstrap Laws run on the first tick. A Law registered after ticking starts
waits for the tick that captures its registration and queued additions to publish,
then becomes eligible on the following tick. A registration arriving during an
active tick waits for the next capture/publication before activation. This prevents
new Laws from running against a Prime that predates their queued initial state.
Intents addressed to inactive Laws remain pending until activation; they are not
silently consumed by the staging tick. No mutable candidate reads bypass this
publication boundary.

The World aggregates these declarations using RuntimeType. One Intent class has
one receiver Law; a Law may accept many Intent classes. Core knows no gravity,
collision, health, shape, mesh or gameplay policy. Applications supply the complete
resolution logic through their Law subclasses and typed capability interfaces.

A Value contains per-tick state, not active update logic. Construct a new Value
from local calculation results rather than modifying an object retained by Prime.
Copying an outer object with mutable references is not a safe snapshot. Immutable
configuration may be shared; anything whose changes affect future evolution must
be versioned. The same rule applies to Law members and world-level timer/RNG data.

Intent contracts define target validation, ordering and consume/reject behavior.
Intents and Events are distinct class hierarchies, not FacetValue envelopes.
Events retain the presentation information needed even if their referenced Form
has already disappeared. Producer/receiver contracts and write ownership remain
validated without inventing another type system.

## Tick execution and failure policy

```text
pin Prime[N], latch live registrations/Laws and external Intent/structural batches
    -> create Slate/candidate with staged external additions and unpublished Event buffer
    -> execute eligible ordered Laws (each at most once)
         read Prime[N], consume Intents, calculate locally
         write Slate, send Intents, stage Events
    -> validate candidate and apply registered structural cleanup
    -> atomically publish complete Prime[N+1]
    -> expose the committed tick's Events
```

Law order is causal request order, not sequential visibility of state writes.
Each Law may internally use jobs, SIMD, solver iterations and physics substeps.
The World advances one authoritative tick at a time; readers can retain older
PrimeViews independently. Atomic publication need not copy unchanged storage.

Intent delivery:

- External inputs are latched at tick start; later arrivals wait for the next tick.
- A Law sends to an active receiver that has not run: eligible in this tick.
- Requests for registered but inactive receivers remain pending until activation.
- A Law sends to an already executed receiver, or to itself: next tick.
- There is no API for selecting an arbitrary future eligibility tick.

Pending Intents are transient runtime data, not Prime state. The MVP promises no
reliable delivery, replay or recovery. If a Law or candidate preparation fails,
keep the last published Prime, discard Slate and unpublished Events, permit
Intent loss, report the failure and stop advancement. Do not retry automatically
or claim that mutated backend solver state was restored. A future resumable
physics adapter needs an explicit checkpoint or isolated candidate-state protocol.

Events never feed Simulation causality. Publish them only after their state
version commits. A bounded stream with tick/sequence and consumer cursors avoids
replaying an event when rendering one Prime multiple times. Slow consumers may
lose old events on overflow in the MVP; they must not receive uncommitted events.

## MVP: multiple bodies, two Laws

The scene contains one finite static ground and multiple falling dynamic boxes.
The architecture permits spheres later; high-quality general physics is not the
MVP goal. Its target is runtime ownership, data access, multi-body solving,
structural changes, routing and independent presentation.

| Facet | Its versioned Value |
| --- | --- |
| TransformFacet | Parent FormId and actual local position/orientation; roots store world pose. |
| MotionFacet | Actual linear and angular velocity. |
| BodyFacet | Axis-aligned box half-extents in metres, mass, friction and restitution. |
| ContactFacet | Set of Forms touching at the end of the tick. |
| CollisionStatsFacet | Cumulative number of contact beginnings. |
| VisualFacet | Mesh handle, box half-extents and color metadata; the current white-model renderer ignores color. |

Ground: Transform + Body + Contact + Visual.
Dynamic box: Transform + Motion + Body + Contact + CollisionStats + Visual.

For this demo only, Transform + Body selects collision participants, and adding
Motion selects bodies integrated by DynamicsLaw. This composition rule is not a
permanent engine distinction between static, dynamic and kinematic bodies. No
`dynamic` flag is needed for the MVP. Absence of Motion does not prohibit future
teleport or kinematic semantics.

This split replaces the earlier six-field SpatialProperty proposal for the MVP.
Acceleration and angular acceleration are not yet persistent fields. Matrices
remain derived data, built and cached by consumers for their reference origin.
Spatial values are resolved actual values, not controller targets. Requests such
as teleport remain subject to the application's resolution rules.

### DynamicsLaw

DynamicsLaw owns Transform, Motion, Contact and CollisionStats runtime updates.
It loads all participants into a local workspace, applies gravity, integrates,
then jointly detects and resolves dynamic/dynamic and dynamic/ground contacts.
Do not advance each body independently against the other bodies' old transforms.
The Law writes final values only after its local solve completes.

Contact sets are symmetric and contain one relation per Form pair, regardless of
contact-point count. Empty means not touching; no duplicate boolean is required.
Use an explicit contact tolerance so depenetration does not erase resting contact.
Compare against Prime's previous contact sets:

```text
began  = current - previous
ended  = previous - current
stayed = current intersect previous
```

Increment each participating CollisionStatsFacet for each new peer; optional
stats must not be read unconditionally from every collision participant. Emit one
contact-begin event per unordered pair. Resting/sliding contact does not count
again. This measures contact beginnings, not impact strength. Contacts that both
begin and end between published tick boundaries may be absent from these sets;
recording every transient impact is outside this MVP statistic.

After solving, a generated body's final `position.y < destroyBelowY` causes a
DestroyFormIntent to LifetimeLaw. The request uses the computed result, not a
reread of old Prime or Slate.

### LifetimeLaw

Execution order is `DynamicsLaw -> LifetimeLaw`. LifetimeLaw defines and accepts
DestroyFormIntent, merges duplicate requests, rejects stale targets, and owns
creation/removal plus persistent generation progress and RNG state. It consumes
same-tick deletion requests, then applies generation rules:

- Simulation-time spawn interval at least 10 ms (at most 100 per second).
- At most 1000 generated dynamic bodies; ground is excluded.
- Capacity includes accepted deletions and already staged creations.
- Do not accumulate spawn credit while at capacity.
- Spawn above the finite ground, with vertical initial velocity zero.
- Default horizontal speed is uniform in [0, 0.5] m/s; direction uniform in [0, 2*pi).
  `LifetimeOptions::maximumHorizontalSpeed` can change the speed limit.

Choose birth region, ground extent and friction so some bodies can reach an edge
with these small velocities. Not every body must leave the ground. Mold creation
initializes the whole Facet composition. Published new bodies enter dynamics on
the next tick.

When a Form is removed, the physics extension's registered cleanup removes its
ID from surviving ContactFacets before publication. This acts only on the
candidate's structural consistency; it is not a second DynamicsLaw execution or
a general Slate read interface. Removing a reference does not increment collision
statistics. The default MVP need not emit synthetic contact-end events on removal.

## Simulation and Presentation

Simulation has causal authority; Presentation only observes. Pure observation
cameras, particles and visual-only animation belong to Presentation. Animation or
IK affecting movement, collision or damage belongs to Simulation.

```text
Simulation:    Prime[N] -> DynamicsLaw -> LifetimeLaw -> checkin -> Prime[N+1]
Presentation:  acquire PrimeView -> build visual snapshot -> render -> repeat
```

Presentation consumes PrimeViews plus Events at an independent cadence. Rendering
may interpolate retained versions, but must define discontinuities for creation,
deletion and teleports before enabling interpolation. Derived presentation values
never overwrite authoritative state. Platform input reaches Simulation through
an ingress producer, not through an authoritative renderer callback.

## Spatial precision and physics boundary

Keep the existing spatial system's precision guarantees:

- WorldCoordinate is a 128-bit integer absolute coordinate; LocalCoordinate is a
  signed 64-bit offset. WorldVector aliases and Rotation express engine space.
- PhysicalScale describes a power-of-ten world-unit size. Convert to physical
  floating-point units only after exact integer rebasing to a local origin.
- `spatial::toLocal`, `toWorld` and integer rotation utilities preserve absolute
  precision; do not convert cosmic-scale absolute coordinates to float first.
- Velocities need fractional physical units and must not reuse integer-position
  storage without an explicit scale/precision contract.

A DynamicsLaw may consume GNfiz, but GNfiz has no E2 dependency. Physics substeps
belong to the World tick's causal timeline. The old independent PhysicalSnapshot
writeback and Form::live workflow is superseded. Backend continuation state needs
explicit ownership; a CPU snapshot wrapper does not version mutable GPU buffers.
Standalone fiz determinism or reverse-time aspirations are not promises of this
World MVP.

## Existing visual architecture to preserve

Use the monolithic `garnet/GNengine2.h`. Presentation uses the basis services:

- `basis::Platform` provides the host window and OS events.
- `basis::Assets` retains registered GPU meshes/textures in simple lookup tables,
  with a built-in box containing positions and normals. No loading or material system is required.
- `basis::Visual::Tableau` is plain data: camera, world-unit scale, object mesh IDs
  and transforms, clear values, and reserved environment data. It owns no GPU work.
- `extractTableau()` adapts committed Prime data into this presentation snapshot.
- `basis::Visual` draws opaque white models with fixed directional and ambient
  diffuse lighting using FX2 LambertianKernel. Texture/environment inputs are not
  consumed by this initial implementation.
- Visual directly acquires, uploads, draws, submits and presents through gpu2;
  there is no RDG dependency or frame graph. Frames complete serially for simplicity.
- Positions are rebased against the camera and converted to metres before FX2.
  Object scale is a mesh multiplier; the built-in box spans [-1, 1].
- One-time uploads survive abandoned recording. GPU resources, submission and
  readback stay inside Visual, independent of the simulation tick cadence.

Platform provides the host window and event adapter independently of World
simulation; presentation retains it while using the window or graphics surface.
The existing Being/RuntimeType and Ref/AutoRef ownership conventions remain useful
where applicable. Public interfaces expose contracts, not concrete world storage.

## Validation and implementation status

### Current refactor status (2026-10-05)

The ECS-style World runtime is a working MVP. It preserves extensible objects:
Form is the entity, Facet supplies immutable component configuration and typed
methods, FacetValue supplies versioned state, and Law performs system updates.
The former plain-value/schema-ID prototype has been replaced with the existing
RuntimeType protocol.

| Area | Implemented behavior |
| --- | --- |
| Composition and ownership | Stable Forms, typed Facets/Values, required-Facet validation and exact-concrete-type writer ownership. |
| Tick publication | All Laws read the same Prime; Slate is write-only; candidate validation precedes whole-tick publication; retained views preserve older versions. |
| Requests and observations | Receiver-defined Intents support same-tick or next-tick routing; Events become observable only after publication. |
| Live additions | Forms, Facets and Laws may be added while running; late Laws activate after their initialization publishes. |
| Spatial state | Transform Values own parent references and local poses; candidate validation rejects cycles and missing parents; Form has no hierarchy. |
| Simulation and presentation | DynamicsLaw runs before LifetimeLaw; an independent presentation thread renders committed snapshots through Platform, Assets and Visual. |

The implementation is not yet a packed ECS storage engine. Private storage uses
maps grouped by concrete type and polymorphic values; a tick copies candidate
container structure while sharing unchanged immutable payloads. Packed SoA or
archetype storage and parallel Law scheduling are not implemented. Laws currently
execute serially in explicit order.

### Physics readiness and GNfiz integration

The active World sample already runs gravity, multiple-box collision response,
persistent symmetric contacts, contact-begin statistics/events, bounded spawning
and out-of-bounds deletion. Its DynamicsLaw uses E2's local axis-aligned-box
solver; it does not invoke a GNfiz solver backend. Integrating GNfiz rigid-body or
soft-body solving requires a Law adapter with explicit ownership of backend
continuation state and a failure protocol consistent with Prime/Slate publication.
The earlier independent PhysicalSnapshot/Form::live integration is superseded.

E2 already shares `GN::fiz::UnitOfTime` (`std::chrono::nanoseconds`).
`World::tick()` and `LawContext::dt` use positive integer nanosecond durations;
numerical Laws convert to floating-point seconds locally for integration.
Sharing this type does not constitute solver integration.

The demo solver uses substeps and iterative overlap resolution. It has no
continuous collision detection (CCD): it does not test the swept motion between
sampled positions, so sufficiently fast bodies can tunnel through thin obstacles.
Rotation/spin response, arbitrary collision shapes and general compound/kinematic
support are also outside this MVP. Acceleration fields remain deferred.

Failed ticks preserve the previous Prime, discard unpublished state/events and
halt advancement. Reliable Intent delivery, automatic retry, backend checkpoint
recovery, deterministic replay and reverse-time World execution are not supplied.
Explicit deferral to an arbitrary future tick is also outside the MVP; requests
sent to the currently executing Law become eligible next tick.

## Public application extension example

This example defines an actual capability object with a nested per-version Value
and nested Intent. The Law owns updates; capability methods provide typed reads
and requests. All runtime types use the existing inheritance metadata.

```cpp
#include <garnet/GNengine2.h>

using namespace GN;
using namespace GN::e2;

struct ChargeFacet : Facet {
    GN_REGISTER_RUNTIME_TYPE(Facet);

    struct Value : FacetValue {
        GN_REGISTER_RUNTIME_TYPE(FacetValue);
        int charge = 0;
        Value(): FacetValue(TYPE_INFO()) {}
        Ref<FacetValue> clone() const override {
            return referenceTo(new Value(*this));
        }
    };

    struct Add : Intent {
        GN_REGISTER_RUNTIME_TYPE(Intent);
        FormId target;
        int amount;
        Add(FormId id, int n): Intent(TYPE_INFO()), target(id), amount(n) {}
        Ref<Intent> clone() const override {
            return referenceTo(new Add(*this));
        }
    };

    ChargeFacet(): Facet(TYPE_INFO()) {}
    const RuntimeType::TypeInfo & valueType() const override {
        return Value::TYPE_INFO();
    }
    Ref<Facet> clone() const override {
        return referenceTo(new ChargeFacet(*this));
    }
    const Value * read(const PrimeView & view, FormId id) const {
        return view.get<ChargeFacet>(id);
    }
    bool requestAdd(World & world, FormId id, int amount) const {
        return world.submit(Add(id, amount));
    }
};

struct ChargeLaw : Law {
    GN_REGISTER_RUNTIME_TYPE(Law);
    ChargeLaw(): Law(TYPE_INFO()) {}
    LawContract contract() const override {
        return {"charge", {&ChargeFacet::TYPE_INFO()},
                {&ChargeFacet::Add::TYPE_INFO()}, false, {}};
    }
    void tick(LawContext & c) override {
        for (auto id : c.prime.query<ChargeFacet>()) {
            ChargeFacet::Value next(*c.prime.get<ChargeFacet>(id));
            for (const auto & intent : c.intents) {
                const auto * add = RuntimeType::cast<const ChargeFacet::Add>(intent.get());
                if (add && add->target == id) next.charge += add->amount;
            }
            c.slate.set<ChargeFacet>(id, next);
        }
    }
};

bool runChargeExample(Universe & universe) {
    auto world = World::create(universe, "charge example");
    auto facet = referenceTo(new ChargeFacet);
    if (!world || !world->registerFacet(*facet)) return false;
    auto mold = Mold::create(universe, "charged form",
        {{facet, referenceTo(new ChargeFacet::Value)}});
    if (!mold) return false;
    auto id = world->createForm(*mold);
    if (!id || !world->addLaw(referenceTo(new ChargeLaw))) return false;

    auto before = world->primeSnapshot();
    auto form = before->form(id);
    auto capability = form->getFacet<ChargeFacet>(*before);
    if (!capability || !capability->requestAdd(*world, id, 3) || !world->tick(UnitOfTime(10000000))) return false;
    auto after = world->primeSnapshot();
    return capability->read(*before, id)->charge == 0 &&
           capability->read(*after, id)->charge == 3;
}
```

Applications can also subclass Form through `Mold::FormFactory`, preserving the
reserved FormId; custom mutable causal fields still belong in versioned Values.
For world-level state, derive from FacetValue, call `registerState<T>()` and
`initializeState(value)` for missing state, declare its RuntimeType in the owner's writes, then use
`PrimeView::state<T>()` and `Slate::setState(value)`.

To require another capability, override `requirements()` and return pointers such
as `&TransformFacet::TYPE_INFO()`. To emit notifications, derive Event, preserve its
complete dynamic type in `clone()`, declare it in `LawContract::events`, and call
`LawContext::emit()`. Intent routing and Event producer declarations name concrete
runtime types. Clone implementations must produce independent mutable payloads;
retaining mutable aliases in a clone violates the snapshot contract.
