# Assignment: Dynamic GPU Buffer Upload — Frame-in-Flight Ring Buffering

---

## Goals

### 1. Efficiency

  1.a  No CPU-GPU sync point unless absolutely necessary.
       The ring-slot / GPU-completion-token model enforces this: the CPU only waits when
       it is about to overwrite a slot the GPU is still reading — an event that should be
       extremely rare with N=2 slots and typical GPU/CPU cadence.  A full GPU drain is
       removed from the hot path entirely.

  1.b  Minimize memory copies — both CPU-side and GPU-side.
       Copies are expensive.  Every extra copy is counted and justified.
       The three Level 2 upload mechanisms have different copy counts:

         BLOB mechanism (2 copies total):
           Copy 1: user data → owned blob (at argument-build time).
           Copy 2: blob → GPU buffer (at execute time).
           Simplest lifetime; acceptable for small, infrequent data.

         HOST_MAP mechanism (1 copy, or 0 with write-callback):
           Raw-pointer path  → 1 copy: user data → host-visible GPU memory (memcpy).
           Write-callback path → 0 copies: user writes directly into mapped memory.
           No intermediate blob.  Best for small, frequently-updated data (UBOs).

         STAGED mechanism (2 copies — unavoidable, but the second is a GPU copy):
           Copy 1: user data → host-visible staging slot (CPU; 1 or 0 with callback).
           Copy 2: GPU blit: staging → device-local GPU buffer.
           Device-local memory gives fastest GPU reads.  Best for large data.

       Level 3 chooses which mechanism to use based on actual usage and scenario.
       Level 2 exposes all three without prescribing when to use each.

### 2. Intuitive / Easy to use

  App code (Level 3 and above) should never deal with backend-specific types
  (VkBuffer, ID3D12Resource, MTLBuffer), ring indices, backend completion tokens,
  keepAlive lists, or upload mechanism details directly.

  Level 3 effects are subgraph builders: setters update CPU state; build() creates
  and returns Workflow objects ready to submit to RenderGraph.

  Usage pattern — Level 3 (SharedShaderConstants as subgraph builder):

    // One-time setup:
    auto sharedConsts = SharedShaderConstants::create(db, "scene", {.gpu = gpu});

    // Per frame (CPU state updates — no GPU touch):
    sharedConsts->setViewInformation(camera);
    sharedConsts->setDirectLightingInformation(lights);

    // build() snapshots state, creates upload workflow(s), returns them:
    auto uploadWf = sharedConsts->build(rg);         // internally uses HOST_MAP+ring(2)
    auto drawWf   = myEffect->build(rg, drawParams); // uses sharedConsts->getSet0Group()

    // submit both — RenderGraph orders them by artifact dependency:
    rg->submit({.workflows = {uploadWf, drawWf}});

  Usage pattern — Level 2 (direct use of GpuBufferUpload):

    // Setup (mechanism choice is explicit at Level 2):
    auto upload = GpuBufferUpload::create(db, "my-ubo", {
        .gpu       = gpu,
        .size      = sizeof(MyUBO),
        .mechanism = GpuBufferUpload::Mechanism::HOST_MAP,
        .ringSlots = 2,
    });

    // Per frame (raw pointer — 1 copy):
    wf->appendTask("upload-ubo", upload, GpuBufferUpload::A::make(&myUbo, sizeof(myUbo)));
    drawArgs.resources[0][0][0] = upload->currentBufferView();

    // Per frame (write callback — 0 copies):
    wf->appendTask("upload-ubo", upload, GpuBufferUpload::A::make([&](void* dst, uint64_t cap) {
        new(dst) MyUBO(myUbo);   // in-place construct directly into mapped GPU memory
    }));

### 3. Extensibility

  The ring-slot / GPU-completion-token / keepAlive model must support the following future
  extensions without a redesign:

  3.a  Per-draw dynamic-offset buffer (Vulkan dynamic UBO offset / D3D12 root CBV offset):
       Instead of one buffer per draw call (too many descriptor bind calls), all per-draw
       payloads for a frame are sub-allocated from a single large ring-slot buffer.
       Each draw call specifies a different offset into that buffer.
       This maps to a "suballocating upload pool" that shares one buffer across many
       draws with increasing offsets.  The ring-slot lifecycle and completion-token tracking
       are identical; only the allocation scheme differs.
       → Plan: introduce UploadPool artifact/action in a follow-up assignment.
         UploadBuffer can serve as the single-allocation degenerate case.

  3.b  Streaming texture uploads (video playback etc.):
       Per-frame texture uploads need the same two-phase (CPU → staging → GPU image) model
       as GPU_OPTIMAL frequency, plus image layout transitions (Vulkan) / resource state
       transitions (D3D12) / blit (Metal) instead of buffer-to-buffer copies.
       The slot / completion-token / keepAlive model applies directly.
       → Plan: introduce UploadTexture action in a follow-up assignment.
         Its Slot struct is identical except the backing resource is a GPU image.

  Design rule: isolate the ring-slot lifecycle (wait → release keepAlive → write → record
  keepAlive → advance → notifyCompletion) into a reusable helper so UploadBuffer,
  UploadPool, and UploadTexture all share the same machinery without duplicating it.

### 4. No API-specific concepts in the public interface; respect the four levels

  The public RDG API (headers under src/inc/) must be implementable by any GPU
  backend.  API-specific types must never appear in public headers at any level.

  Prohibited in public API:
    VkBuffer, VkImage, VkFence, VkSemaphore, VkDescriptorSet, rapid_vulkan::*, vk::*
    ID3D12Resource, IDXGISwapChain, MTLBuffer, MTLTexture, Metal::*, D3D12::*
    SubmissionID, eHostVisible, eDeviceLocal, vkCmd*, DXGI_*, MTL_*

  Level boundary rules (see also rdg/README.md):
    Level 2 (actions.h, artifacts.h): expresses MECHANISM, not policy or frequency.
      → GpuBufferUpload exposes BLOB / HOST_MAP / STAGED + ringSlots.
      → No "STREAM" / "DYNAMIC" / "GPU_OPTIMAL" frequency concepts here.
    Level 3 (pipeline.h, ...): expresses POLICY.
      → SharedShaderConstants internally chooses HOST_MAP+ring(2) for UBOs.
      → The app never sees the mechanism choice.

  Backend-to-mechanism mapping (internal; for implementers only):

    Mechanism  │ Vulkan                      │ D3D12                  │ Metal
    ───────────┼─────────────────────────────┼────────────────────────┼──────────────────
    BLOB       │ host-coherent VkBuffer      │ UPLOAD heap buffer     │ shared MTLBuffer
    HOST_MAP   │ ring of host-coherent       │ ring of UPLOAD heap    │ ring of shared
               │ VkBuffers; map/unmap        │ buffers; Map/Unmap     │ MTLBuffers; contents
    STAGED     │ device-local VkBuffer +     │ DEFAULT heap buffer +  │ private MTLBuffer +
               │ host-visible staging ring   │ UPLOAD heap staging    │ shared staging + blit

    GPU token  │ rapid_vulkan::SubmissionID  │ ID3D12Fence + value    │ MTLSharedEvent + val
    (internal) │ (never public)             │ (never public)         │ (never public)

## Design

### A. Core abstraction: GpuUploadSlot (internal backend helper — NOT public API)

Used internally by UploadBufferVulkan (and later UploadPoolVulkan, UploadTextureVulkan).
This struct lives in src/core/rdg/ (backend layer) and may reference backend-specific
types freely.  It must never appear in src/inc/ (public headers).

  // Vulkan backend version (vk-upload-slot.h, not public):
  struct GpuUploadSlot {
      rapid_vulkan::CommandQueue::SubmissionID submissionId;  // Vulkan-specific; internal only
      DynaArray<AutoRef<RefCounted>>           keepAlive;

      bool isReady() const;                                    // submissionId done or empty
      void waitUntilReady(rapid_vulkan::CommandQueue & q);     // wait + warning log if needed
      void recycle();                                          // clear keepAlive, reset token
      void addKeepAlive(AutoRef<RefCounted> ref);
      void notifyCompletion(rapid_vulkan::CommandQueue::SubmissionID id);
  };

  // D3D12 backend would have an equivalent struct using ID3D12Fence.
  // Metal backend would use MTLSharedEvent.
  // All backends share the same LIFECYCLE; only the completion-token type differs.

UploadBufferVulkan owns N GpuUploadSlots.  Each slot also owns its backend buffer(s).

### B. GpuBufferUpload — Level 2 public API (actions.h)

  // Level 2: mechanism is explicit; frequency/usage policy belongs in Level 3.
  struct GpuBufferUpload : public Action {

      // Upload mechanism — choose at creation time.
      // See rdg/README.md §"Dynamic Data Upload" for full pros/cons.
      enum class Mechanism {
          BLOB,       // 2 copies: user data → blob → GPU buffer.
                      // Simplest lifetime. Acceptable for small/infrequent data.
          HOST_MAP,   // 1 copy (or 0 with callback): write directly to mapped
                      // host-visible GPU memory.  Best for small per-frame UBOs.
          STAGED,     // 2 copies: CPU → staging → device-local GPU buffer.
                      // Best GPU read bandwidth; good for large/less-frequent data.
      };

      struct CreateParameters {
          AutoRef<GpuContext> gpu;
          uint64_t            size;
          Mechanism           mechanism  = Mechanism::HOST_MAP;
          uint32_t            ringSlots  = 2;   // 1 = no ring-buffering
      };

      struct A : public Arguments {
          // Set exactly one of data/dataSize or writeFn.

          // Raw-pointer path: backend memcpy(dst, data, dataSize).  1 copy.
          // Pointer NOT retained past execute().
          const void * data     = nullptr;
          uint64_t     dataSize = 0;

          // Write-callback path: writeFn(mappedPtr, capacity) called synchronously.
          // 0 copies when user writes directly. Need not outlive execute().
          std::function<void(void * dst, uint64_t capacity)> writeFn;

          static AutoRef<A> make(const void * data, uint64_t size);
          static AutoRef<A> make(std::function<void(void*, uint64_t)> fn);

          void addToReadWriteList(ArtifactReadWriteList&) const override;
      };

      virtual GpuResourceView currentBufferView() const = 0;

      static GN_API AutoRef<GpuBufferUpload> create(ArtifactDatabase&, const StrA&,
                                                     const CreateParameters&);
  };

Note: the action was previously named `UploadBuffer`; renamed `GpuBufferUpload` to
match the Level 2 naming convention (`Gpu` prefix, verb-noun order).

### C. HOST_MAP mechanism — Vulkan backend execute() flow (internal)

  // Internal to GpuBufferUploadVulkan; never visible to app code.
  struct Slot : GpuUploadSlot {
      rapid_vulkan::Ref<rapid_vulkan::Buffer> vkBuffer;  // host-coherent, preallocated
  };

  execute(args):
    uint32_t next = (mCurrentSlot + 1) % mRingSlots;
    mSlots[next].waitUntilReady(queue);   // wait only if GPU still reading slot (rare)
    mSlots[next].recycle();               // keepAlive empty for HOST_MAP
    {
        rapid_vulkan::Buffer::Map<uint8_t> m(*mSlots[next].vkBuffer);
        if (args->writeFn)  args->writeFn(m.data, mSize);
        else                memcpy(m.data, args->data, args->dataSize);
    }
    mCurrentSlot = next;
    // No keepAlive entry needed: vkBuffer is preallocated and owned by the Slot.

  D3D12: Ring of UPLOAD heap ID3D12Resources; Map/Unmap instead of Buffer::Map.
  Metal: Ring of shared MTLBuffers; contents pointer instead of Map.

### D. STAGED mechanism — Vulkan backend execute() flow (future Phase 2.4, internal)

  // Internal to GpuBufferUploadVulkan; never visible to app code.
  struct StagingSlot : GpuUploadSlot {
      rapid_vulkan::Ref<rapid_vulkan::Buffer> stagingBuffer;  // host-visible, preallocated
  };

  Members (internal):
      rapid_vulkan::Ref<rapid_vulkan::Buffer> mGpuBuffer;       // device-local, single
      StagingSlot                             mSlots[mRingSlots];
      uint32_t                                mCurrentSlot = mRingSlots - 1;

  execute(args):
    uint32_t next = (mCurrentSlot + 1) % mRingSlots;
    mSlots[next].waitUntilReady(queue);
    mSlots[next].recycle();
    {
        rapid_vulkan::Buffer::Map<uint8_t> m(*mSlots[next].stagingBuffer);
        if (args->writeFn)  args->writeFn(m.data, mSize);
        else                memcpy(m.data, args->data, args->dataSize);
    }
    // GPU-side copy + barrier (Vulkan-specific command recording):
    vkCmdCopyBuffer(cmdBuf, stagingBuffer, mGpuBuffer, ...);
    vkCmdPipelineBarrier(cmdBuf, TRANSFER_WRITE → UNIFORM_READ, ...);
    // stagingBuffer owned by Slot; no extra keepAlive entry needed.
    mCurrentSlot = next;

  currentBufferView() → mGpuBuffer (single device-local buffer, not the staging slot).

  D3D12: Map UPLOAD heap → CopyBufferRegion to DEFAULT heap → resource barrier.
  Metal: Fill shared MTLBuffer → blitEncoder.copy() to private MTLBuffer.

### E. GPU completion notification (internal plumbing, backend-specific)

  Public model: after execute() is called on an UploadBuffer action, the RDG guarantees
  that the backing memory for that slot will not be reused until the GPU has finished
  reading it.  The mechanism is backend-specific and never visible to app code.

  Vulkan backend (internal):
    SubmissionContextVulkan holds:
        DynaArray<UploadBufferVulkan*> activeUploads;  // reset each submission

    UploadBufferVulkan::execute() registers this into activeUploads.

    After CommandQueue::submit() returns a SubmissionID:
        for (auto * ub : ctx.activeUploads) ub->notifyCompletion(id);

    UploadBufferVulkan::notifyCompletion(id):
        mSlots[mCurrentSlot].notifyCompletion(id);   // delegates to GpuUploadSlot

  D3D12 backend (future): same pattern, ID3D12Fence value instead of SubmissionID.
  Metal backend (future): same pattern, MTLSharedEvent signaled value instead.

### F. currentBufferView()

  HOST_MAP:  → GpuResourceView of mSlots[mCurrentSlot].vkBuffer,
               type=UNIFORM, offset=0, size=mSize.
  STAGED:    → GpuResourceView of mGpuBuffer (single device-local buffer).
  BLOB:      → GpuResourceView of the buffer the blob was uploaded to.

  Called by the workflow-builder AFTER execute() runs for the upload task
  (i.e., from within build() of a Level 3 subgraph builder, or explicitly
  at Level 2 after adding the upload task to the workflow).

### G. SharedShaderConstants — Level 3 subgraph builder

  SharedShaderConstants is a Level 3 object.  It follows the subgraph builder pattern:
  setters update CPU state only; build() snapshots state and returns upload workflow(s).

  Level 3 policy decision (hidden from app):
      Camera + lighting UBOs are small (240 + 784 bytes) and updated every frame.
      → HOST_MAP mechanism with ringSlots=2 is used internally.
      The app never sees this choice.

  Members (internal to SharedShaderConstantsVulkan):
      AutoRef<GpuBufferUpload> mCameraUpload    (HOST_MAP, ringSlots=2, 240 B)
      AutoRef<GpuBufferUpload> mLightingUpload  (HOST_MAP, ringSlots=2, 784 B)
      GlobalCameraUBO          mPendingCamera   (CPU-side, updated by set*())
      DirectLightingUBO        mPendingLighting (CPU-side, updated by set*())

  Public API change (Level 3):
      // Old: prepareSubmission(Submission&)  ← removed
      // New: build() — returns upload workflow; fits Level 1 RenderGraph model.
      Workflow * build(RenderGraph & rg);

  build() implementation:
      auto wf = rg->createWorkflow("shared-constants-upload");
      wf->appendTask("camera",   mCameraUpload,   A::make(&mPendingCamera,   sizeof(...)));
      wf->appendTask("lighting", mLightingUpload, A::make(&mPendingLighting, sizeof(...)));
      mSet0Group->setResourceViews(0, 0, {mCameraUpload->currentBufferView()});
      mSet0Group->setResourceViews(1, 0, {mLightingUpload->currentBufferView()});
      return wf;

  App usage:
      sharedConsts->setViewInformation(camera);
      auto uploadWf = sharedConsts->build(rg);   // one line; mechanism is hidden
      auto drawWf   = pbrEffect->build(rg, ...); // reads Set 0 from sharedConsts
      rg->submit({.workflows = {uploadWf, drawWf}});

### H. waitForIdle removal

  After Phase 2 is done, every upload slot is guarded by its own SubmissionID.
  Command buffers will be tagged with SubmissionIDs too (Phase 6).
  The only wait left in the hot path is inside GpuUploadSlot::waitUntilReady(),
  which fires only when N frames pile up — a rare event in normal operation.
