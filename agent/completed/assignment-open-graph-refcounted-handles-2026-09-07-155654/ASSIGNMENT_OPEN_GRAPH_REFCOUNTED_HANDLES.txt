# Assignment: Refactor Open Graph Opaque Handles to Refcounted Entities

---

## Goals

Replace the raw opaque pointer handles used by RDG2 open graph (`ArtifactPtr`,
`TokenPtr`, and `NodePtr`) with typed refcounted entity handles. The new public
types should still hide implementation details: each handle type is a small
public interface, normally a pure virtual `Entity` subclass with only the
minimal utility/query methods that callers need.

The refactor should make handle lifetime management natural and explicit.
Graph-created artifacts, tokens, and nodes should stay alive while callers hold
references. The graph implementation should no longer depend on raw opaque
pointers plus FOURCC validation alone for lifetime safety.

Artifact handles should remember the graph that created them with
`WeakRef<Graph>`. Graph methods should reject artifacts, tokens, and nodes that
belong to a different graph. Token and node handles should follow the same
ownership/misuse detection rule unless we agree on a narrower scope.

Artifacts should keep only the latest published content. Publishing new content
releases the graph's reference to the previous content immediately. Callers that
need older content are responsible for holding their own `AutoRef<Entity>` to
that older content.

## Design

The feature spec is maintained separately next to this plan:

- `agent/SPEC_OPEN_GRAPH_REFCOUNTED_HANDLES.md`

Use that spec as the source of truth for proposed API shape, ownership model,
artifact content semantics, misuse detection, and resolved design decisions.

### Resolved Decisions

Agreed:

- Keep `ArtifactPtr`, `TokenPtr`, and `NodePtr` names, but make them aliases to
  `AutoRef<Artifact>`, `AutoRef<Token>`, and `AutoRef<Node>`.
- Make `Artifact`, `Token`, and `Node` public `Entity` subclasses.
- Use `WeakRef<Graph>` as each handle's graph back-reference.
- Handles do not keep their graph alive. After graph destruction, operations
  that need graph access fail when weak-ref promotion fails.
- Reject cross-graph handles; no cross-graph handle use case is currently known.
- Expose no additional public utility methods on `Artifact`, `Token`, or `Node`
  initially.
- Keep FOURCC as a pure implementation detail in private concrete handle
  classes.
- Use `AutoRef` internally only where ownership/lifetime requires it. Prefer raw
  pointers/references for hot graph-internal links when another owner guarantees
  the handle cannot be deleted while the link is used.
- Prefer references or const references over pointers for internal function
  parameters when the caller has already handled null and the callee does not
  accept null.
- Defer moving selected graph methods onto handle classes to a possible second
  phase. The `WeakRef<Graph>` stored in each handle makes that possible later,
  but this first phase keeps behavior on `Graph`.

--- WORKFLOW / CONVENTIONS ---

- Do not start coding until the plan and open questions are agreed.
- Use `feature/rdg/main` as the base branch unless told otherwise.
- Use a `wip/rdg2/<topic>` branch for implementation after plan approval.
- Keep public API changes and call-site updates in explicit verified steps.
- Preserve existing user/manual changes.
- Use `AutoRef<T>` for RDG/gpu2 ownership.
- Use `RuntimeType::cast<T>()`; do not use `dynamic_cast`.
- Prefer references/const references for required internal parameters after
  null validation at public entry points.
- Keep comments meaningful and durable. Use them to explain why a lifetime,
  ownership, validation, or ordering choice is necessary; record assumptions,
  invariants, and purpose. Avoid comments that merely restate what the next line
  does.
- Prefer focused tests for misuse detection and lifetime behavior.
