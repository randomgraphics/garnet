# Build, Test, CI, and Platform Map

This entry summarizes configured workflows inspected at baseline `27d39c986` on
`wip/agent-harness`. It records repository configuration; later runtime observations
are dated separately below. See [`coverage.md`](coverage.md) for scan scope and
limitations.

## Build system

- Root `CMakeLists.txt` defines C++20 on `GNcore-objects` and defaults
  `GN_BUILD_SAMPLES`, `GN_BUILD_TOOLS`, and `GN_BUILD_TESTS` to ON.
- Normal builds use `env/bin/build.py`, which configures CMake into named build
  variants. Do not use raw CMake for ordinary development; use it only for a
  focused CMake investigation.
- Variants: `d` Debug, `p` RelWithDebInfo, `r` Release, `c` Linux-only coverage,
  `x` clean. `-c` is configure-only and `-C` is build-only; positional `c` means
  coverage. Android uses `-a`; Linux clang uses `--clang`.
- On Windows, run Python scripts via `python.exe`; environment setup is
  `. env\garnet.ps1`. Unix environment setup is `source env/garnet.rc`.
- Root CMake probes OpenGL and Vulkan; generated `features.h` reflects detected
  platform features. Core CMake sets legacy DirectX feature flags on Windows and
  Vulkan from `VULKAN_FOUND`. These flags indicate configured availability, not
  that every module has an implemented backend.

## Windows sandbox build limitation

**Current requirement: run Windows builds outside the agent sandbox, in the normal
user environment.** For agent execution, use the tool's approved unsandboxed
execution mechanism. From the repository root, use the repository's Python virtual
environment and normal build wrapper:

```powershell
.\.pyvenv\Scripts\python.exe env\bin\build.py d
```

Confirmed by runtime investigation on 2026-11-02 with MSBuild 18.10.1 and MSVC/PDB
components 14.51.36260.0:

- Sandboxed `/m:8` builds failed after ten 30-second attempts to connect to MSBuild
  worker named pipes. `ZERO_CHECK` completed; the failure was in
  `ResolveProjectReferences`, before C++ compilation.
- `/m:1` bypassed that failure but compilation still reported C1902. A minimal
  single-file `/Zi /FS` compile reproduced it; the PDB RPC API returned
  `EC_RPC (23): unable to connect: timeout waiting for mspdbsrv.exe (0x800705B4)`.
  Matching tool versions and fresh PDB files did not resolve the sandbox failure.
- The same existing build directory and toolchain built successfully outside the
  sandbox with `cmake --build build/windows.vc.d -j8 --config Debug --verbose`
  (exit code 0). This raw CMake invocation was a diagnostic comparison; ordinary
  builds should continue to use `env/bin/build.py`.

`Start-Process` inside the sandbox does not move its child process into the normal
user execution environment. A matching `whoami` result does not establish equivalent
sandbox permissions or IPC access. Changing only the launcher or using `/m:1` is
therefore not a complete workaround.

Evidence: local, Git-ignored logs under `build/windows.vc.d/` include
`msbuild-node-diagnostics/MSBuild_CommTrace_PID_67764.txt`,
`pdb-sandbox-diagnostics/api-rpc-sandbox.log`, and `cmake-user-context.log`.
These are observations of the tested Windows agent environment, not a claim about
every Windows sandbox implementation. Recheck after sandbox or toolchain updates.

## Test and lint entrypoints

| Command | Configured behavior | Source |
|---|---|---|
| `env/bin/cit.py` | Style/lint then test suite | `env/bin/cit.py` |
| `env/bin/cit.py -l` | Style/lint only | `env/bin/cit.py` |
| `env/bin/cit.py -t` | Unit and internal tests plus selected finite sample test modes | `env/bin/cit.py`, `src/test/CMakeLists.txt` |
| `env/bin/cit.py -i [filter]` | Internal test binary | `env/bin/cit.py` |
| `env/bin/cit.py -u [filter]` | Unit-test binary | `env/bin/cit.py` |
| `env/bin/cit.py -c` | Linux coverage workflow through `code-coverage.py` | `env/bin/cit.py`, `env/bin/code-coverage.py` |

`GNtest-unit-tests` source is generated by `src/test/ut/CMakeLists.txt` using
`cxxtestgen.py`. `GNtest-internal` links production object files and Catch2, and
loads sorted `internal-test.cmake` fragments found recursively under core/tool
test roots (`src/test/internal/CMakeLists.txt`). Tests have not been run as part
of this initialization.

Formatting uses `env/bin/format-all-sources.py`; the repo guide and
`garnet-build-test` skill list check/format modes. Confirm flags with the script's
current `--help` if using a less common option.

## Coverage

The Garnet gcov/gcovr coverage workflow is Linux-only and uses a dedicated
Debug/`--coverage` build directory. Windows MSVC can collect native C++ line
coverage separately with Visual Studio's `Microsoft.CodeCoverage.Console`, but
that collector is not wired into Garnet's build/CIT/CI workflow; see
[`code-quality-assessment.md`](code-quality-assessment.md) and the
[`garnet-code-quality-assessment` skill](../skills/garnet-code-quality-assessment/SKILL.md).
`env/bin/code-coverage.py` supports GCC and a clang path using `llvm-cov gcov`;
the CircleCI matrix runs coverage only in Linux GCC and uses `coverage` instead
of its debug variant. Coverage instrumentation is scoped to core, sample, tool,
and test CMake directories so vendored libraries are excluded. See
[`garnet-code-coverage`](../skills/garnet-code-coverage/SKILL.md) for report files,
optimization rationale, and gcda pitfalls.

Coverage reports default to `<build-variant>/output/coverage/`; quality
assessment joins default to `<build-variant>/output/quality/`; build-specific
settings belong in `<build-variant>/output/config/`; run logs and exit-status
files belong in `<build-variant>/output/logs/`. The `/build*/`
ignore rule keeps these generated files out of Git, and each build directory
keeps its own outputs so platform/compiler/configuration results do not
overwrite one another.

## Configured CI matrix

The CircleCI config defines Windows native builds, Linux GCC builds, Linux Clang
builds, and Android container builds. Linux GCC's variants are coverage/profile/
release; Windows, Linux Clang and Android use debug/profile/release. CircleCI
hydrates recursive shallow submodules and LFS assets. The matrix does not prove
that all jobs run on every branch or that this worktree passes them; inspect job
filters and CI run records for that claim.

## Platform/backend interpretation

- The root README is a high-level introduction, not a full backend status table.
- `src/core/gpu2/README.md` describes Vulkan as active and D3D12/Metal as stubs.
- CMake conditionally generates FX2/RDG2/gpu2 sample shader outputs when Vulkan
  is found; individual sample targets may therefore differ across configurations.
- Core CMake still reports legacy D3D and OpenGL feature flags according to the
  platform and discovered libraries. Do not equate an old feature macro with an
  active gpu2 backend.
- macOS has root-level CMake handling but is absent from the inspected CircleCI
  job list; CI absence is not proof that local macOS builds are impossible.
- Android is configured by the project wrapper with NDK API/platform 29 and the
  selected ABI; Docker guidance/image is linked from the skill index.

## Recheck checklist

For a concrete platform-support claim, inspect in the same worktree:

1. `CMakeLists.txt` and relevant module/sample subdirectory conditions.
2. Generated feature macros and backend factory selection.
3. CI executor, variant matrix, filters, and test steps.
4. Tests/samples that actually instantiate the backend.
5. A current build/run result for the target platform when behavioral support
   rather than configured support is being claimed.
