# Assignment: Code Coverage Build Variant and Function-Level CIT Report

---

## Goals

Add a dedicated code coverage build variant so that coverage instrumentation never
touches the `d`/`p`/`r` builds that developers use daily, and so that CIT can produce a
detailed function-level test coverage report on demand.

The existing debug build must not carry `--coverage`. Coverage instrumentation is heavy
enough that adding it to `d` degrades or breaks the build every developer depends on; the
overhead belongs in its own isolated build directory that is only configured when someone
explicitly asks for coverage.

The report must be trustworthy at function granularity. That drives the optimization level
choice: gcov function records disappear when the compiler inlines a function, so the
variant compiles at `-O0`. Measured on this toolchain (GCC 15.2, gcov 15.2):

| flags | functions reported for a 4-function TU | notes |
| --- | --- | --- |
| `-O0 -g` | 4 | `static inline helper` keeps its own record |
| `-Og -g` | 3 | `helper` inlined into `main`, record gone |
| `-O2 -g` | 3 | additionally reports an executed function as 0% |

`-Og` enables 28 optimizers that `-O0` does not, including `-finline`, `-ftree-dce`,
`-ftree-ccp`, `-freorder-blocks` and `-ftoplevel-reorder`. Because this codebase marks many
header-defined helpers `inline` by convention, `-Og` would silently drop a large share of
`src/inc/garnet/**` from the function report while the report still looked plausible.

---

## Design

### Build variant

`c` becomes the coverage variant and `clean` moves to `x`. `c` previously meant clean;
`AGENTS.md`, `QWEN.md` and `agent/skills/garnet-build-test/SKILL.md` all document the old
meaning and must be updated together with the code.

Coverage is Linux-only for now. On any other platform `build.py c` fails with an explicit
message rather than silently producing an uninstrumented build.

The variant reuses `CMAKE_BUILD_TYPE=Debug` and only adds `--coverage`, writing to its own
directory `build/linux.gcc.c`:

- CMake's `CMAKE_CXX_FLAGS_DEBUG` default is exactly `-g` with no `-O` flag, so GCC already
  lands on `-O0` implicitly. The chosen "-O0 -g, isolated directory" configuration therefore
  needs no extra optimization flag.
- `GN_BUILD_DEBUG_ENABLED` is derived from `CMAKE_BUILD_TYPE STREQUAL "Debug"` in the root
  `CMakeLists.txt`, so debug features and assertions stay ON, matching the `d` variant.

### Instrumentation scope

Everything except vendored third-party code. `GN_enable_code_coverage()` is a directory-scope
helper called from `src/core`, `src/sample`, `src/tool` and `src/test` rather than from the
repository root, so `add_compile_options` never reaches `src/3rdparty`. `src/test` calls it
*after* its own `add_subdirectory(3rdparty)`, which keeps Catch2 uninstrumented.

### Binary discovery

`garnet-utils.search_for_the_latest_binary_ex()` picks the newest binary by mtime. Its
variant list becomes a parameter defaulting to `[".c", ".d", ".p", ".r"]`, so a checkout
that only built the coverage variant still resolves binaries for a plain `cit.py -t`. The
accepted tradeoff is that a freshly built instrumented binary outranks an older debug one
and therefore runs slower. Coverage reporting pins `COVERAGE_BUILD_VARIANTS = [".c"]`, so a
report can never be taken from a binary that was not instrumented.

On Windows the per-config output folder for `.c` maps to `Debug`, matching the
`CMAKE_BUILD_TYPE` the variant configures with.

### CI pipeline

`.circleci/config.yml` ran `[debug, profile, release]` for all four job types through one
shared `&build-parameters` / `&build-matrix` anchor pair. Linux now runs
`[coverage, profile, release]` through a second anchor pair, leaving Windows and Android on
debug. Coverage replaces the Linux debug job rather than adding to it: same `-O0`
`CMAKE_BUILD_TYPE=Debug` configuration, plus instrumentation and a report.

`build-linux-gcc`'s test step branches on the variant. For coverage it runs
`env/bin/code-coverage.py --no-build`, which clears stale `.gcda`, runs the same test set
`cit.py -t` would, and generates the report. `build-linux-clang` has no test step, so it
only proves the coverage variant compiles under clang; it never needs the `llvm-cov` that
report generation would require.

### Report

gcovr 8.6, added to `env/requirements.txt`. Three outputs under
`build/linux.gcc.c/coverage/`, which is already covered by the `/build*/` gitignore rule:

- `index.html` via `--html-details` — browsable per-file line coverage.
- `coverage.json` via `--json` — per-function records carrying `demangled_name`, `lineno`,
  `execution_count` and `blocks_percent`.
- `functions.md` — generated from `coverage.json`: per-directory function rollup plus the
  list of never-executed functions. This is the "detailed function-level" deliverable.

Console output ends with `--print-summary` totals for lines, functions and branches.

Stale `.gcda` files are deleted before each run; gcov accumulates counters, so skipping this
would silently inflate every subsequent measurement.

--- WORKFLOW / CONVENTIONS ---

- The `d`, `p` and `r` variants must produce byte-identical cmake command lines to before
  this change. Verify by comparing configure output.
- `GN_BUILD_CODE_COVERAGE` defaults OFF; when OFF no coverage flag may reach any target.
- Never instrument `src/3rdparty` or `src/test/3rdparty`.
- Coverage reports land under the build directory so `/build*/` keeps them out of git.
- New python scripts follow the existing `env/bin` style: argparse, `garnet-utils` helpers,
  `utils.rip()` for fatal errors.
- Commit style `"<scope>(<area>): <description> (Phase N.M)"`.
