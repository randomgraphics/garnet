# Assignment: RDG — Cross-submission dependencies (task-level pipelining)
---
## Goals
Support automatic dependencies across multiple `RenderGraph::submit()` calls when independent authors submit workflows that read/write the same logical RDG `Artifact`s.

Key scenario:
- Submission S1 contains task(s) that write an artifact `R`.
- Submission S2 contains task(s) that read `R`.
- S1 and S2 are authored independently; neither knows the other’s internal workflow structure.

Required behavior:
- The system automatically infers the dependency via declared artifact read/write sets and enforces correct ordering.
- To maximize throughput, **do not** require “S1 finished on GPU” as the coarse gate for “S2 can start”.
- Allow **task-level pipelining** across submissions: if S2’s first use of `R` only depends on an early task in S1, S2 should be allowed to prepare/record/submit as soon as the required producer work for `R` has been *submitted* (or otherwise produces a waitable token), without waiting for unrelated work in S1.
---
## Design

### Assumptions and scope (initial)
- Cross-submission dependency inference uses **stable resource identity**. The simplest supported identity is a shared `Artifact *` instance referenced by arguments in both submissions.
- “Correctness” means no read observes incomplete writes on the GPU; “performance” means we preserve maximal CPU/GPU overlap by avoiding submission-wide blocking.
- Current RDG execution model prepares and executes tasks sequentially inside a submission, and dependency-graph building is currently per-submission and pointer-identity-based.

### Target model: global, task-level dependency resolution
We extend dependency tracking from “workflows inside a submission” to “tasks across all in-flight submissions”.

Core idea:
- Build a **global dependency graph** where each RDG task becomes a node.
- Add edges based on artifact read/write conflicts using the same rule as existing intra-submission ordering (newer depends on older when WAR/WAW/RAW hazards exist).
- Scheduling picks any node whose dependencies are satisfied and runs its `prepare()` / `execute()` even if it belongs to a later submission.

This enables pipelining:
- If S1 has tasks A(write R), B(unrelated), and S2 has task C(read R),
  then C can run as soon as A’s “GPU waitable token” exists (see below) and does not need to wait for B.

### Split the problem into two planes

#### (A) CPU scheduling plane (prepare/execute ordering)
We need a single scheduler (or small pool) that sequences task `prepare()` and `execute()` calls across submissions:
- Avoid “one thread per submission” that blocks entire submissions behind others.
- Instead, treat submissions as “task containers” and schedule at task granularity.

Scheduler responsibilities:
- Maintain a ready queue of tasks whose dependencies are satisfied.
- Ensure per-workflow ordering constraints remain intact (tasks inside a workflow are sequential).
- Ensure global artifact hazard constraints are satisfied (RAW/WAR/WAW).

#### (B) GPU synchronization plane (queue submission + waits)
Some tasks’ `execute()` may record commands and submit GPU work. Cross-task correctness requires:
- When a task writes artifact `R`, it produces a **GPU completion token** (timeline semaphore value / queue submission id / fence handle).
- When a later task reads `R`, its `execute()` must ensure the GPU will **wait** on the last-writer token before using `R`.

To maximize overlap, the dependency should usually be:
- **wait-on-submission** (GPU token that represents “writer commands are enqueued in-order before reader commands”)
not necessarily
- **wait-on-completion** (full GPU finish), unless the API forces it.

In Vulkan terms:
- If work is submitted to the same queue, ordering can often be established by ensuring correct submit order (and appropriate pipeline barriers), so the “token” can be “writer submit happened before reader submit”.
- If work crosses queues, we need explicit semaphores (likely timeline semaphores) to avoid host blocking.

### Artifact identity across submissions
Minimum viable requirement:
- Cross-submission dependencies are inferred when both submissions reference the same `Artifact *` instance (shared object identity).

Future extension (optional, but plan for it):
- A canonicalization/registry mapping `ResourceId`/name → canonical `Artifact` so independently-authored submissions can refer to “the same resource” without pointer sharing.

### Observability / debugging
Add high-signal diagnostics:
- When a task is delayed, report which artifact edge(s) are blocking it and the producing task.
- Provide per-submission and global views: “in-flight tasks”, “last-writer for artifact”, “pending waits”.
