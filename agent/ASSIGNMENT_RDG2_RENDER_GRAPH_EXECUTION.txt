# Assignment: RDG2 Render Graph Execution Layer

---

## Goals

Implement the next RDG2 render graph attempt, independent from the current open
graph implementation unless specific concepts prove useful. RDG is currently a
playground for graph designs; this assignment is render graph take 2.

The new layer should let callers declare quest inputs and outputs, compile those
declarations into dependency order, execute independent quests in parallel where
possible, gather outputs from all quests, and submit produced GPU payloads in one
ordered `gpu2::GpuContext::submit()` call for the first implementation.

The design must support both frame-scoped executions and long-lived background
executions. Background producers, such as compute-shader lightmap updates, should
be able to execute incrementally outside a frame boundary and publish relics that
regular frame rendering can consume as data inputs.

This background-producer requirement is the original reason for RDG2's versioned
artifact model. Relics are the data handoff between producers that finish
whenever they finish and frame executions that need a stable captured state.

Concrete helpers such as shared shader constants, skybox, and PBR shading are
validation clients only. They should not define RDG concepts, and RDG should not
know what those effects mean.

---

## Design

The design spec is maintained separately:

- `agent/SPEC_RDG2_RENDER_GRAPH_EXECUTION.md`

Use that spec as the source of truth for phases, dependency rules, output
gathering, artifact/relic discipline, and the SCC/PBR boundary.

### Vocabulary

Agreed public terms:

- `Artifact` — named graph data item.
- `Relic` — immutable published state of an artifact.
- `Quest` — declared executable unit.
- `Plan` — compiled dependency graph of quests and artifact accesses.
- `Execution` — active running instance of a plan.

Public retained objects use `XxxRef = AutoRef<Xxx>`. Reserve `Handle` for
repo/table-managed opaque IDs such as the existing repo handle system.

### Execution Phases

The layer has four phases:

1. Quest declaration: each quest declares artifact reads/writes and explicit
   dependencies without executing.
2. Compile/build: declarations are validated, artifact reads/writes are mapped
   to relic producers and consumers, dependencies are analyzed, dead quests are
   culled, and a deterministic plan is produced.
3. Execution: ready quests execute when dependencies are satisfied. Quests emit
   relic publications, diagnostics, and sealed GPU payloads, but do not submit
   GPU work directly by default. Execution owns scheduling and may run
   independent ready quests in parallel.
4. Gathering/submission: all emitted GPU payloads are gathered in compiled order
   and submitted to `gpu2::GpuContext` in one batch.

### Artifact Discipline

`ArtifactRef` may cross threads, but outside execution it is an opaque immutable
identity. Only execution-owned APIs may resolve concrete relic versions, query
latest relics, or publish new relics. Declaration and compilation should use
symbolic relic selectors such as current-known-good, latest-at-execution-start,
or next-published instead of concrete version numbers.

### Boundaries

- `rdg2` render graph code handles artifacts, relics, quests, plans,
  executions, dependencies, scheduling, and gathered outputs.
- The current open graph is reference material only. Borrow useful concepts, but
  do not force this design to reuse open graph APIs or internals.
- `gpu2` continues to own GPU resources, GPU payloads, state tracking, submit,
  pump, and idle waits. Keep gpu2 vocabulary as-is.
- SCC/PBR/skybox adapters may be added as tests or sample clients, but the core
  API must not depend on them.

--- WORKFLOW / CONVENTIONS ---

- Keep the core render graph API free of SCC/PBR/skybox terminology.
- Treat this as render graph take 2, not an extension of the current open graph.
- Keep gpu2 vocabulary as-is: use GPU resource and GPU payload for concepts
  inherited from gpu2.
- Use `Entity` plus `AutoRef` references for retained public objects: Artifact,
  Relic, Quest, Plan, and Execution.
- Use `XxxRef` for `AutoRef<Xxx>` public references; reserve `Handle` for
  repo/table-managed opaque IDs.
- Prefer small, verified slices that leave the tree buildable.
- Use `AutoRef<T>` for RDG/gpu2 ownership.
- Use `RuntimeType::cast<T>()`; do not use `dynamic_cast`.
- Public API declarations need Doxygen comments.
- Use concise comments only for invariants, ownership, dependency rules, or
  ordering constraints.
- Treat artifacts as opaque immutable identities outside execution.
- Use relics as the data handoff from background producers to frame consumers.
- Keep artifact/relic API method names short, such as `publish`, `latest`, and
  `wait`, inside execution-owned APIs.
- Preserve user/manual changes and avoid unrelated refactors.
- Prefer one verified task per commit when turning this plan into commits.
