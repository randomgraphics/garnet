# Assignment: Dynamic GPU Buffer Upload — Frame-in-Flight Ring Buffering

---

## Goals

### 1. Efficiency

  1.a  No CPU-GPU sync point unless absolutely necessary.
       The ring-slot / GPU-completion-token model enforces this: the CPU only waits when
       it is about to overwrite a slot the GPU is still reading — an event that should be
       extremely rare with N=2 slots and typical GPU/CPU cadence.  A full GPU drain is
       removed from the hot path entirely.

  1.b  Minimize memory copies — both CPU-side and GPU-side.
       Copies are expensive.  Every extra copy is counted and justified:

         STREAM frequency (target: 1 copy or 0):
           Raw-pointer path  →  1 copy: user data → CPU-writable GPU memory (memcpy).
           Write-callback path → 0 copies: user constructs data directly in mapped memory.
           NO intermediate "blob" copy is allowed.  The A object must NOT contain a blob.

         GPU_OPTIMAL frequency (target: 2 copies — unavoidable):
           Copy 1:  user data → CPU-visible staging memory.
           Copy 2:  GPU blit: staging → GPU-local memory.
           GPU-local memory gives fastest GPU reads.  The 2-copy cost is paid once per
           upload, not once per shader invocation — worthwhile for large or infrequent data.

         Write-callback eliminates Copy 1 even in the GPU_OPTIMAL case when the user can
         write structured data directly into mapped staging memory.

### 2. Intuitive / Easy to use

  App code should never deal with any backend-specific types (VkBuffer, ID3D12Resource,
  MTLBuffer), ring indices, backend completion tokens, or keepAlive lists directly.
  The public RDG API hides all of that behind API-agnostic concepts.

  Usage pattern for shared constants:

    // One-time setup (application init):
    auto sharedConsts = SharedShaderConstants::create(db, "scene", {.gpu = gpu});

    // Per frame:
    sharedConsts->setViewInformation(camera);
    sharedConsts->setDirectLightingInformation(lights);
    sharedConsts->prepareSubmission(submission);     // adds upload actions; updates descriptors

    submission.add(draw, drawArgs);                 // drawArgs use sharedConsts->getSet0Group()

  For direct use of UploadBuffer:

    // Setup:
    auto upload = UploadBuffer::create(db, "my-ubo",
                      {.gpu = gpu, .size = sizeof(MyUBO), .frequency = GpuDataFrequency::STREAM});

    // Per frame (raw pointer — 1 copy):
    submission.add(upload, UploadBuffer::A::make(&myUbo, sizeof(myUbo)));
    drawArgs.resources[0][0][0] = upload->currentBufferView();

    // Per frame (write callback — 0 copies):
    submission.add(upload, UploadBuffer::A::make([&](void * dst, uint64_t cap) {
        new(dst) MyUBO(myUbo);   // in-place construct directly into mapped GPU memory
    }));

### 3. Extensibility

  The ring-slot / GPU-completion-token / keepAlive model must support the following future
  extensions without a redesign:

  3.a  Per-draw dynamic-offset buffer (Vulkan dynamic UBO offset / D3D12 root CBV offset):
       Instead of one buffer per draw call (too many descriptor bind calls), all per-draw
       payloads for a frame are sub-allocated from a single large ring-slot buffer.
       Each draw call specifies a different offset into that buffer.
       This maps to a "suballocating upload pool" that shares one buffer across many
       draws with increasing offsets.  The ring-slot lifecycle and completion-token tracking
       are identical; only the allocation scheme differs.
       → Plan: introduce UploadPool artifact/action in a follow-up assignment.
         UploadBuffer can serve as the single-allocation degenerate case.

  3.b  Streaming texture uploads (video playback etc.):
       Per-frame texture uploads need the same two-phase (CPU → staging → GPU image) model
       as GPU_OPTIMAL frequency, plus image layout transitions (Vulkan) / resource state
       transitions (D3D12) / blit (Metal) instead of buffer-to-buffer copies.
       The slot / completion-token / keepAlive model applies directly.
       → Plan: introduce UploadTexture action in a follow-up assignment.
         Its Slot struct is identical except the backing resource is a GPU image.

  Design rule: isolate the ring-slot lifecycle (wait → release keepAlive → write → record
  keepAlive → advance → notifyCompletion) into a reusable helper so UploadBuffer,
  UploadPool, and UploadTexture all share the same machinery without duplicating it.

### 4. No API-specific concepts in the public interface

  The public RDG API (headers under src/inc/) must be implementable by any GPU backend:
  Vulkan today, D3D12 and Metal in the future.  API-specific types and concepts must
  never appear in public headers.

  Prohibited in public API:
    VkBuffer, VkImage, VkFence, VkSemaphore, VkDescriptorSet, rapid_vulkan::*, vk::*
    ID3D12Resource, IDXGISwapChain, MTLBuffer, MTLTexture, Metal::*, D3D12::*
    SubmissionID, eHostVisible, eDeviceLocal, vkCmd*, DXGI_*, MTL_*

  The public API expresses WHAT the app needs (semantics), not HOW the backend does it.

  Key public-API design rule — use the GpuDataFrequency enum to express upload semantics:

    enum class GpuDataFrequency {
        STREAM,       // Updated every frame or multiple times per frame.
                      // Prioritize CPU-write bandwidth; GPU reads from shared memory.
                      // Backends: host-coherent ring (Vulkan), UPLOAD heap ring (D3D12),
                      //           shared ring (Metal).

        DYNAMIC,      // Updated occasionally (not every frame, more than once).
                      // Backend chooses best trade-off between CPU and GPU access cost.

        GPU_OPTIMAL,  // Uploaded rarely (once or near-once); GPU reads must be fastest.
                      // CPU uploads via staging copy; GPU data lives in fast local memory.
                      // Backends: device-local + staging (Vulkan), DEFAULT heap (D3D12),
                      //           private + blit (Metal).
    };

  This replaces the old HOST_VISIBLE_RING / DEVICE_LOCAL_STAGED naming, which was
  Vulkan-specific and meaningless on other backends.

  Backend-to-public mapping:

    GpuDataFrequency  │ Vulkan                     │ D3D12                │ Metal
    ──────────────────┼────────────────────────────┼──────────────────────┼───────────────────
    STREAM            │ Ring of host-coherent       │ Ring of UPLOAD heap  │ Ring of shared
                      │ VkBuffers                  │ ID3D12Resources      │ MTLBuffers
    ──────────────────┼────────────────────────────┼──────────────────────┼───────────────────
    DYNAMIC           │ Host-visible or staged      │ UPLOAD or DEFAULT    │ managed or shared
                      │ (implementation decides)   │ (implementation)     │ (implementation)
    ──────────────────┼────────────────────────────┼──────────────────────┼───────────────────
    GPU_OPTIMAL       │ Device-local + staging      │ DEFAULT + UPLOAD     │ private + blit
                      │ VkBuffer ring              │ staging ring         │ staging ring

    GPU completion    │ rapid_vulkan::SubmissionID  │ ID3D12Fence          │ MTLSharedEvent
    token (internal)  │ (never public)             │ (never public)       │ (never public)

    keepAlive         │ DynaArray<AutoRef<>>        │ same (backend impl)  │ same (backend impl)
    (internal)        │ held until fence done       │ held until fence     │ held until event

## Design

### A. Core abstraction: GpuUploadSlot (internal backend helper — NOT public API)

Used internally by UploadBufferVulkan (and later UploadPoolVulkan, UploadTextureVulkan).
This struct lives in src/core/rdg/ (backend layer) and may reference backend-specific
types freely.  It must never appear in src/inc/ (public headers).

  // Vulkan backend version (vk-upload-slot.h, not public):
  struct GpuUploadSlot {
      rapid_vulkan::CommandQueue::SubmissionID submissionId;  // Vulkan-specific; internal only
      DynaArray<AutoRef<RefCounted>>           keepAlive;

      bool isReady() const;                                    // submissionId done or empty
      void waitUntilReady(rapid_vulkan::CommandQueue & q);     // wait + warning log if needed
      void recycle();                                          // clear keepAlive, reset token
      void addKeepAlive(AutoRef<RefCounted> ref);
      void notifyCompletion(rapid_vulkan::CommandQueue::SubmissionID id);
  };

  // D3D12 backend would have an equivalent struct using ID3D12Fence.
  // Metal backend would use MTLSharedEvent.
  // All backends share the same LIFECYCLE; only the completion-token type differs.

UploadBufferVulkan owns N GpuUploadSlots.  Each slot also owns its backend buffer(s).

### B. UploadBuffer::A — no blob, write directly to GPU-accessible memory (PUBLIC API)

  struct A : public Arguments {
      // --- Set exactly one of the following ---

      // Raw-pointer path: backend calls memcpy(dst, data, dataSize).  1 copy.
      // Pointer NOT retained past execute().  API-agnostic.
      const void * data     = nullptr;
      uint64_t     dataSize = 0;

      // Write-callback path: backend calls writeFn(mappedPtr, capacity).  0+ copies.
      // writeFn is called synchronously inside execute(); need not outlive execute().
      // Callback receives a plain void*; no backend-specific types are exposed.
      std::function<void(void * dst, uint64_t capacity)> writeFn;

      static AutoRef<A> make(const void * data, uint64_t size);
      static AutoRef<A> make(std::function<void(void*, uint64_t)> fn);

      void addToReadWriteList(ArtifactReadWriteList&) const override;
  };

The callback signature (void*, uint64_t) is fully API-agnostic: the backend maps
whatever memory is appropriate (VkBuffer, D3D12 UPLOAD resource, MTLBuffer) and passes
the CPU pointer.  The app never knows or cares which.

There is NO blob field.  Data goes directly into backend-mapped memory during execute().
This keeps STREAM frequency at 1 copy (raw) or 0 copies (callback).

### C. STREAM frequency — Vulkan backend execute() flow (internal)

  // Internal to UploadBufferVulkan; never visible to app code.
  struct Slot : GpuUploadSlot {
      rapid_vulkan::Ref<rapid_vulkan::Buffer> vkBuffer;  // host-coherent ring slot
  };

  execute(args):
    uint32_t next = (mCurrentSlot + 1) % MAX_UPLOAD_SLOTS;
    mSlots[next].waitUntilReady(queue);   // wait only if GPU still reading slot
    mSlots[next].recycle();               // keepAlive always empty for STREAM
    {
        rapid_vulkan::Buffer::Map<uint8_t> m(*mSlots[next].vkBuffer);
        if (args->writeFn)  args->writeFn(m.data, mSize);
        else                memcpy(m.data, args->data, args->dataSize);
    }
    mCurrentSlot = next;
    // No keepAlive needed: vkBuffer is preallocated and ring-managed by the Slot itself.

  D3D12 equivalent: Ring of UPLOAD heap ID3D12Resources; Map/Unmap instead of
                    rapid_vulkan::Buffer::Map.  Lifecycle identical.
  Metal equivalent: Ring of shared MTLBuffers; contents pointer instead of Map.

### D. GPU_OPTIMAL frequency — Vulkan backend execute() flow (future Phase 2.4, internal)

  // Internal to UploadBufferVulkan; never visible to app code.
  struct StagingSlot : GpuUploadSlot {
      rapid_vulkan::Ref<rapid_vulkan::Buffer> stagingBuffer;  // host-visible, preallocated
  };

  Members (internal):
      rapid_vulkan::Ref<rapid_vulkan::Buffer> mGpuBuffer;   // device-local, single buffer
      StagingSlot mStagingSlots[MAX_UPLOAD_SLOTS];
      uint32_t    mCurrentStaging = MAX_UPLOAD_SLOTS - 1;

  execute(args):
    uint32_t next = (mCurrentStaging + 1) % MAX_UPLOAD_SLOTS;
    mStagingSlots[next].waitUntilReady(queue);
    mStagingSlots[next].recycle();
    {
        rapid_vulkan::Buffer::Map<uint8_t> m(*mStagingSlots[next].stagingBuffer);
        if (args->writeFn)  args->writeFn(m.data, mSize);
        else                memcpy(m.data, args->data, args->dataSize);
    }
    // Record GPU-side copy + barrier into current command buffer (Vulkan-specific):
    vkCmdCopyBuffer(cmdBuf, stagingBuffer, mGpuBuffer, ...);
    vkCmdPipelineBarrier(cmdBuf, TRANSFER_WRITE → UNIFORM_READ, ...);
    mStagingSlots[next].addKeepAlive(wrap(mStagingSlots[next].stagingBuffer));
    mCurrentStaging = next;

  currentBufferView() → mGpuBuffer (the single GPU-local buffer, not the staging slot).

  D3D12 equivalent: Map UPLOAD heap resource → CopyBufferRegion to DEFAULT heap → barrier.
  Metal equivalent: Fill shared MTLBuffer → blitEncoder.copy() to private MTLBuffer.

### E. GPU completion notification (internal plumbing, backend-specific)

  Public model: after execute() is called on an UploadBuffer action, the RDG guarantees
  that the backing memory for that slot will not be reused until the GPU has finished
  reading it.  The mechanism is backend-specific and never visible to app code.

  Vulkan backend (internal):
    SubmissionContextVulkan holds:
        DynaArray<UploadBufferVulkan*> activeUploads;  // reset each submission

    UploadBufferVulkan::execute() registers this into activeUploads.

    After CommandQueue::submit() returns a SubmissionID:
        for (auto * ub : ctx.activeUploads) ub->notifyCompletion(id);

    UploadBufferVulkan::notifyCompletion(id):
        mSlots[mCurrentSlot].notifyCompletion(id);   // delegates to GpuUploadSlot

  D3D12 backend (future): same pattern, ID3D12Fence value instead of SubmissionID.
  Metal backend (future): same pattern, MTLSharedEvent signaled value instead.

### F. currentBufferView()

  HOST_VISIBLE_RING: → GpuResourceView of mSlots[mCurrentSlot].vkBuffer
                        type=UNIFORM, offset=0, size=mSize.
  DEVICE_LOCAL_STAGED: → GpuResourceView of mGpuBuffer (single device-local buffer).

  Called by app AFTER execute() runs (i.e., after adding upload action to submission,
  and before adding draw action).

### G. SharedShaderConstants integration

  Camera + lighting UBOs are small (240 + 784 bytes), updated every frame.
  → HOST_VISIBLE_RING is the right strategy.

  Members:
      AutoRef<UploadBuffer> mCameraUpload    (HOST_VISIBLE_RING, 240 B)
      AutoRef<UploadBuffer> mLightingUpload  (HOST_VISIBLE_RING, 784 B)
      GlobalCameraUBO       mPendingCamera   (CPU-side, updated on set*Information())
      DirectLightingUBO     mPendingLighting (CPU-side, updated on set*Information())

  prepareSubmission(Submission & s):
      s.add(mCameraUpload,   A::make(&mPendingCamera,   sizeof(mPendingCamera)));
      s.add(mLightingUpload, A::make(&mPendingLighting, sizeof(mPendingLighting)));
      mSet0Group->setResourceViews(0, 0, {mCameraUpload->currentBufferView()});
      mSet0Group->setResourceViews(1, 0, {mLightingUpload->currentBufferView()});

  This is the only call the app needs to make per frame for shared constants.

### H. waitForIdle removal

  After Phase 2 is done, every upload slot is guarded by its own SubmissionID.
  Command buffers will be tagged with SubmissionIDs too (Phase 6).
  The only wait left in the hot path is inside GpuUploadSlot::waitUntilReady(),
  which fires only when N frames pile up — a rare event in normal operation.
