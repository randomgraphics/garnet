# Assignment: Dynamic GPU Buffer Upload — Frame-in-Flight Ring Buffering

## Goal

Add an `UploadBuffer` **action** to the RDG that lets app code upload per-frame dynamic
data (UBOs, per-frame constants, etc.) to the GPU efficiently and safely, without ever
calling `Buffer::setContent()` directly, and without stalling the CPU waiting for the GPU
to finish the previous frame.

"Done" means:
  - Two upload strategies are available (selectable at creation time):
      HOST_VISIBLE_RING   — N ring-buffered host-coherent VkBuffers; single memcpy per frame.
      DEVICE_LOCAL_STAGED — one GPU-local VkBuffer + N host-visible staging slots; two copies
                            but faster GPU reads and compatible with non-coherent GPU memory.
  - User-passed data is ALWAYS copied immediately (inside execute()) — the caller's pointer
    is never held past the call.  The resulting data blob is kept alive for the full GPU
    lifetime of that slot via a per-slot deferred-release list.
  - Per-slot SubmissionID tracking ensures the CPU never overwrites a slot the GPU is
    still reading.  The wait fires only when all N slots are still in-flight (rare).
  - After GPU submit, SubmissionIDs are distributed back to all UploadBuffer actions used
    in that submission.  Slot release (keepAlive list drop + recycling) happens lazily the
    next time that slot is reused.
  - `SharedShaderConstants` is refactored to use `UploadBuffer` actions internally
    (camera UBO + lighting UBO), so app code still just calls `setViewInformation()`.
  - The per-frame `waitForIdle()` full GPU drain is removed; CPU and GPU pipeline N frames
    simultaneously.

## Design Deep Dive

### 1. Why two strategies?

Map/unmap (HOST_VISIBLE_RING):
  + One copy only (CPU → host-visible GPU memory via memcpy).
  + Simple: no command buffer needed for the copy; no pipeline barrier.
  − Host-visible memory is typically in the PCI-E aperture or uncached; GPU reads may be
    slower than from device-local (VRAM) memory, especially for large buffers.
  − Each slot needs its own VkBuffer because GPU reads the buffer while CPU might write
    the next slot — ring-buffering isolates the two.

  Best for: small, frequently-updated constants like UBOs (camera, lights).
            sizeof ≤ a few KB; updated every frame; GPU access overhead is negligible.

Transfer via staging (DEVICE_LOCAL_STAGED):
  + Destination buffer is device-local (VRAM); fastest GPU reads.
  + Works on platforms without coherent host-visible memory (mobile, some discrete GPUs).
  − Two copies: CPU → host-visible staging slot → GPU-local buffer via vkCmdCopyBuffer.
  − Requires a pipeline barrier in the command buffer (TRANSFER_WRITE → SHADER_READ).
  − Staging slots need lifetime tracking; GPU-local buffer is shared (not ring-buffered
    per se, but the copy command provides the write-after-write fence automatically).

  Best for: large buffers (mesh data, texture uploads) that change occasionally;
            device-local performance matters more than upload simplicity.

### 2. User-data lifetime rule

The rule: the UploadBuffer action always owns the data once execute() is called.
  - execute(args) → immediately copies args->data into the slot (for HOST_VISIBLE_RING)
    or into the staging slot (for DEVICE_LOCAL_STAGED).  The raw pointer in args is NOT
    retained past execute().
  - UploadBuffer::A carries data as a self-contained blob (DynaArray<uint8_t>).
  - A::make(const void* data, uint64_t size) copies into the blob immediately.
  - A::make(DynaArray<uint8_t> && data) moves an existing blob into A (zero-copy).
  - The A object itself is held in the slot's keepAlive list until the slot's SubmissionID
    is complete.  This guarantees the data outlives GPU access even if the caller discards
    the A object right after adding to the submission.

### 3. Per-slot deferred-release model

Every ring slot carries:

  struct Slot {
      // Strategy-specific GPU memory:
      rapid_vulkan::Ref<rapid_vulkan::Buffer> vkBuffer;    // host-visible (HOST_VISIBLE_RING)
                                                            // or staging (DEVICE_LOCAL_STAGED)
      // Sync:
      rapid_vulkan::CommandQueue::SubmissionID submissionId;

      // Deferred release: things to keep alive until GPU is done with this slot.
      // Released (in order) at the BEGINNING of the next use of this slot,
      // after submissionId is confirmed done.
      DynaArray<AutoRef<RefCounted>> keepAlive;
  };

Slot lifecycle per use:
  1. Before writing:
       if submissionId is non-empty:
           wait(submissionId)  ← only if truly needed (slot still in-flight)
       drop keepAlive list     ← safe now that GPU is done
       reset submissionId      ← slot is now free
  2. Write data into slot (memcpy or staging copy).
  3. Add A object (and any other transient resources) to keepAlive.
  4. mCurrentSlot = this slot.
  5. After GPU submit: submissionId = <SubmissionID from this frame>.

For DEVICE_LOCAL_STAGED, the staging slot recycles exactly as above.
The GPU-local destination buffer is a single VkBuffer (no ring needed).

### 4. Submission plumbing for SubmissionID distribution

After CommandQueue::submit() returns a SubmissionID, the submission context calls
notifySubmission(id) on every UploadBufferVulkan that participated in this submission.
Each one stores the id in its current slot's submissionId field (step 5 above).

This requires:
  - SubmissionContextVulkan to maintain a list of participating UploadBufferVulkan* objects.
  - UploadBufferVulkan::execute() registers itself into this list.
  - The post-submit hook in CommandBufferManagerVulkan (or SubmissionImpl) iterates the
    list and calls notifySubmission.

### 5. HOST_VISIBLE_RING slot selection and ring-buffer contract

  N = MAX_UPLOAD_SLOTS (start with 2)
  next_slot = (mCurrentSlot + 1) % N

  execute():
    1. Determine next_slot.
    2. If mSlots[next_slot].submissionId non-empty → wait (log warning; should be rare).
    3. Drop mSlots[next_slot].keepAlive.
    4. Map mSlots[next_slot].vkBuffer; memcpy args->blob.data, args->blob.size.
    5. Add args (A object) to mSlots[next_slot].keepAlive.
    6. mCurrentSlot = next_slot.

  currentBufferView() → GpuResourceView pointing to mSlots[mCurrentSlot].vkBuffer,
                         type=UNIFORM, offset=0, size=mSize.

### 6. DEVICE_LOCAL_STAGED slot selection (future phase)

  Staging ring: N host-visible slots (same lifecycle as HOST_VISIBLE_RING above).
  GPU-local buffer: single VkBuffer, device-local, size=mSize, usage=UNIFORM|TRANSFER_DST.

  execute():
    1. Pick next staging slot (same wait/drop logic as above).
    2. Map staging[next]; memcpy.
    3. Record vkCmdCopyBuffer(staging[next] → gpuBuffer).
    4. Record pipeline barrier: TRANSFER_WRITE → (VERTEX|FRAGMENT)_SHADER_READ.
    5. Add staging buffer ref + A object to staging[next].keepAlive.
    6. mCurrentStagingSlot = next.

  currentBufferView() → GpuResourceView pointing to gpuBuffer (the single GPU-local one).

### 7. SharedShaderConstants integration

SharedShaderConstants camera + lighting UBOs are small (240 + 784 bytes) and updated
every frame → HOST_VISIBLE_RING is the right strategy.

SharedShaderConstantsVulkan owns:
  - AutoRef<UploadBuffer> mCameraUpload    (HOST_VISIBLE_RING, 240 bytes)
  - AutoRef<UploadBuffer> mLightingUpload  (HOST_VISIBLE_RING, 784 bytes)
  - GlobalCameraUBO    mPendingCamera    (CPU-side, packed on setViewInformation())
  - DirectLightingUBO  mPendingLighting  (CPU-side, packed on setDirectLighting...)

New method: prepareSubmission(Submission & s):
  - submission.add(mCameraUpload,   UploadBuffer::A::make(&mPendingCamera,   sizeof(mPendingCamera)));
  - submission.add(mLightingUpload, UploadBuffer::A::make(&mPendingLighting, sizeof(mPendingLighting)));
  - mSet0Group->setResourceViews(0, 0, {mCameraUpload->currentBufferView()});
  - mSet0Group->setResourceViews(1, 0, {mLightingUpload->currentBufferView()});

App calls prepareSubmission() once at the top of each frame before any draw actions.

### 8. Removing waitForIdle

Currently CommandBufferManagerVulkan drains all queues after every submission → CPU/GPU
serial.  Once every critical resource (uploaded buffer, command buffer) has per-slot
SubmissionID tracking, waitForIdle in the hot path is replaced by:

  "If all N upload slots are still in-flight, wait for the oldest one."

This is almost always a no-op for N=2 because by the time the CPU finishes recording
frame i+1, the GPU has usually finished frame i.
