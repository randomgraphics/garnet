# Assignment: Replace FX2 geometry, assets, and surfaces with typed GPU kernels
---
## Goals

Provide a simple, typed, graph-independent effect system over gpu2. Kernels
consume GPU buffer/texture views and immediate CPU values. Remove FX2 Geometry,
GeometryAsset, Surface, and Surface::Asset from the final public interface.
Preserve viewer and active FX2 sample behavior while migrating callers. The
suspended E2 Simple-world sample and dependent tests are explicitly excluded.

Expose raster and compute implementations as distinct kernels. Higher-level
code selects implementations; FX2 must not silently switch between them.
Keep SSC's current single GPU version per instance and document its ordering
requirements. Web and mobile portability constrain the design; implementing
all missing platform backends is outside this refactor.

### Module boundaries and transitional code

The viewer owns its importer, hierarchy, navigation, window/swapchain, GPU
resource uploads, and frame ordering. It invokes FX2/gpu2 directly and neither
includes nor calls E2. RDG2 is optional higher-level scheduling, not a new
mandatory dependency to replace E2. Keep print-only import GPU-independent.

ImGuiBackend belongs to FX2 and records against gpu2, with explicit prerequisite
upload output. It does not inherit VisualMoment/VisualOverlay or take an E2
context. E2 clients can wrap it in an application-defined moment; an application adapter can establish this direction without making FX2 depend
on an E2 test scene. Remove GNui2 public headers,
namespace, shader/build targets, and live documentation references.
ImGuiBackend also owns UI context/input integration; these are not generic
Kernel responsibilities. During kernel migration, route its GPU effect logic
through the same typed raster conventions without forcing scene/UI lifecycle
methods into Kernel. Do not invent an additional public UI abstraction merely
to relocate the existing backend.

The viewer may temporarily bind the existing FX2 shaders directly while the
new typed kernels are absent. This bridge must stay tool-private and must be
removed when mesh kernels arrive. Do not duplicate shader sources or create
another public effect/asset framework. Keep this temporary stage buildable.

### Viewer rewrite after the kernel implementation

The current E2-free viewer is a transitional implementation, not the final
viewer design. Once typed mesh/skybox kernels and the FX2 ImGui recording path
are available, rewrite or substantially simplify its rendering integration.
A mechanical replacement of Surface calls or shader bindings is insufficient.
Keep useful importer, hierarchy inspection, navigation, and regression coverage;
replace rendering plumbing wherever that makes the flow simpler.

Use one explicit application flow:
  import/generate CPU scene -> create buffers/textures and record uploads ->
  update input/camera/UI -> acquire target and prepare SSC -> record typed
  model/debug/skybox/ImGui work -> submit in dependency order -> present/read back.

Keep CPU import and print-only inspection independent of GPU initialization.
Share GPU vertex/index buffers and textures across model instances; preserve
full affine instance transforms. Represent prepared inputs as straightforward
application-owned data, not a new Asset hierarchy or generic effect framework.
Select concrete kernels in the viewer; pass typed arguments directly. The
viewer owns render policy (ordering, targets, depth/culling/blending defaults),
while kernels own shader bindings and algorithm-required state.

Keep main.cpp focused on startup and the application loop. Separate import,
resource preparation, rendering, and UI/navigation only where their lifetimes
or responsibilities justify it; avoid creating a framework of tiny wrappers.
Windowed rendering and headless snapshots must use the same scene recording
path, differing only in target/presentation/UI handling. Do not add blur or
mipmap demonstrations to the viewer unless an actual viewer feature needs them.

Delete model-draws.cpp's direct shader/descriptor/UBO packing bridge, its private
FX2 shader-header includes, and its generated-shader build dependency. The
viewer must consume public module APIs only. Remove obsolete comments, options
documentation, and tests tied to abandoned rendering architecture while keeping
user-facing features and meaningful importer/output coverage.

The obsolete Geometry/Surface implementation may remain only to keep unmigrated
clients buildable during staged work; it is not an accepted design to retain.
The final removal includes headers, implementations, tests, examples, and docs.
Do not delete unrelated E2 functionality or importer coverage along with it.

### Kernel contract

Kernel is a small abstract, device-associated interface using existing RCRT64
and AutoRef patterns. Concrete effects expose strongly typed argument schemas
and recording operations. Shader/state implementations and caches stay private.
External derivation must be possible without registering a central effect enum.
Add RasterKernel/ComputeKernel bases only if they provide useful contracts;
the concrete type always makes the execution strategy explicit.

Initial mesh effects: raster PBR, cel, unlit, Lambertian, and skybox kernels.
Image effects: RasterGaussianBlurKernel, ComputeGaussianBlurKernel,
RasterMipmapKernel, and ComputeMipmapKernel. Equivalent variants may share
plain parameter schemas; they remain separate types with no automatic fallback.
Unsupported capabilities or inputs produce actionable failures.

Kernels retain shaders and reusable implementation state. Each invocation
supplies typed GPU resources and values, not persistent string-based bindings.
Steady-state recording must not compile shaders, decode files, wait for GPU
idle, or use blocking setContent/readback calls. Prepare reusable resources
outside the draw loop. Small private constants can use copied immediates or
batched uploads; do not require a new owning wrapper per material or draw.
Reuse gpu2 raster geometry/buffer descriptions rather than introducing another
FX2 mesh owner. Document vertex semantics and optional-attribute requirements;
removing Geometry does not remove the need to validate input layouts.
SSC is required only for effects that actually consume its shared parameters.
Skybox rendering moves from SSC into its typed raster kernel. SSC continues
owning shared environment bindings and the existing constant/upload behavior;
separating the draw operation must not introduce SSC versioning.

### Ownership after removing assets

Geometry generation, file decoding, import, CPU mesh/material descriptions,
GPU buffer/texture creation, and uploads belong to callers or existing lower
level utilities. Identify destinations from actual call sites before moving
code. Preserve procedural box/sphere and viewer functionality; do not replace
Asset with a newly named FX2 resource bundle.

The obsolete E2 MeshVisualFacet/createMeshForm path and its device asset caches
have been removed: all its callers belonged to suspended Simple-world code.
Reuse the existing public VisualFacet::snapshot() -> VisualMoment::record()
extension point. CPU resource preparation remains application-owned; captured
moments retain ordinary GPU resources and typed values. There is no new asset
wrapper, effect-kind switch, or generic untyped Kernel invocation.

An effect-specific moment retains a typed kernel and captured
typed arguments or the immutable CPU inputs needed to prepare them. Its record()
calls that kernel directly. The domain still invokes only VisualMoment::record().
An application can add a new VisualFacet/VisualMoment and a new typed Kernel
without editing E2's central renderer. Direct FX2 users need no E2 adapter.
Keep mutable caches outside captured scene values; do not read live forms or
mutable materials during record(). Preparation services must be usable by custom
moments without casts to private VisualRecordContext or private cache access.

The current public RenderContext exposes raster(), ssc(), and upload(), where
upload work precedes the entire shared raster. This is sufficient for prepared
mesh draws but cannot express postprocessing that consumes preceding draws.
If an E2 client needs postprocessing, extend its bridge with ordered pass boundaries: finish the
active raster, append dependent raster/compute work, and resume a raster only
when requested with explicit attachment load/store behavior. Borrowed raster
references cannot remain valid across a boundary. Ordinary moments continue
sharing a raster; image effects must not masquerade as upload() operations.
This is a documented extension point, not a prerequisite for standalone FX2
blur/mipmap kernels or the E2 typed mesh migration. Do not build an E2-wide
postprocessing framework without a concrete E2 client requiring it.
The application supplies explicit image inputs/outputs and logical ordering;
the domain retains submission/presentation ownership. Do not assume the
swapchain image supports sampling or storage writes; scene postprocessing may
need a separate render texture followed by final composition.

Custom moments receive default camera/light SSC bindings plus selected environment
textures. A concrete custom multiview renderer supplies separate prepared SSC
instances when views share one raster. No automatic scene/view association is
implied; the single-version ordering contract still applies.

Caller-provided GPU data must be initialized before use through ordered GPU
work. Retaining a resource keeps its allocation alive, not its contents stable.
Immediate CPU values are copied during recording. Borrowed input arrays need
not survive a successful record operation. Recorded work retains resources
until it is abandoned or finished; scratch reuse respects GPU completion.
Initial scratch allocations can be separate per invocation; pooling is later
optimization, not a prerequisite or a new public asset abstraction.

### Recording and synchronization

The first implementation selects these small contracts instead of a general
RecordingContext framework:
  - UnlitKernel::record(GpuRaster &, const GpuResourceSet & shared, const Inputs &)
    appends one draw, copies immediate values, and inherits caller states.
  - SkyboxKernel::record(GpuRaster &, const GpuResourceSet & shared) appends the
    fullscreen background draw with its documented depth/cull overrides.
  - Image-kernel contract: record(const Inputs &,
    DynaArray<AutoRef<GpuPayload>> & work) appends a complete ordered sequence.
    Raster and compute variants are separate classes with typed inputs. Build
    work locally and append only after all steps succeed. The caller submits.
    All four image kernels implement this contract; CPU-reference and GPU tests pass.

No new owning geometry/material wrapper or generic named-argument interface is
introduced. The concrete shader programs retain the device resources they need.

Mesh kernels append draws to a caller-owned raster pass, so many objects share
attachments and one pass. A cel surface draw plus outline need not open two
physical render passes. Ordering between different objects stays with callers.

Multipass image kernels record ordered raster passes or compute dispatches
through a minimal recording context/output sink. Reuse GpuRaster, GpuCnC, and
GpuPayload; do not implement another graph or submission scheduler in FX2.
Raster target boundaries are explicit. Do not inject copies or dependent
compute work inside an open physical raster pass.

Separate initialization, prerequisite uploads, and rendering in the invocation
contract. A mesh kernel can append draws to an existing raster while returning
private-uniform uploads to a caller-owned prerequisite recorder; those uploads
must use distinct storage when multiple pending draws require different values.
A multipass kernel returns/appends ordered GPU work whose intermediate steps
cannot be moved into that prerequisite bucket. Phase 1 must demonstrate both
forms with concrete signatures before adding any generalized context API.
Internal lazy initialization must retain its dependency until it is actually
scheduled; recording or caching resources alone does not establish readiness.
SSC retains its explicitly documented existing exception to this policy.

Validate invocation requirements before appending work. On failure, either
append nothing (preferred) or explicitly invalidate the enclosing recording;
never report success with missing passes. Use the project's error conventions.

Texture uses identify mip/layer ranges and sampled/storage/attachment access.
gpu2 owns backend barriers. Prove its tracking handles the examples; changes
must address concrete gaps, not duplicate synchronization in FX2.
Do not reorder uploads/draws, fuse passes, or sort effects across dependencies.
FX2 records work; higher-level code submits/presents. FX2 must not depend on RDG2.

### Raster state

Effective state is the caller's baseline plus documented algorithm-required
kernel overrides. Caller policy controls ordinary culling, depth, blending,
viewport/scissor, and draw ordering. Overrides are scoped to the affected draw
or pass. gpu2 owns native pipeline caching and must include effective state in
its key; do not introduce a duplicate FX2 pipeline cache as part of this design.

Blur/mipmap intermediate passes require full valid output coverage and
replacement writes; disable depth/blending or inherited scissor when these
would invalidate the algorithm. Define output-producing effects separately
from compositing, which can use a caller-controlled raster operation.
Compute kernels have no fixed-function raster-state inheritance.

### Shared and private constants

Keep SSC's current single scene/camera UBO pair per instance. Snapshots capture
CPU values into upload work, not independent GPU UBO versions. Required order:
upload A -> every consumer of A -> upload B -> every consumer of B, including
the associated GPU read/write dependencies. CPU recording can run ahead.
An upload cannot occur between draws in one open raster pass; use pass
boundaries or separate SSC instances when distinct camera values are needed.

Do not gather all SSC uploads before all draws when they target the same UBOs.
Test this explicit contract, not the rejected independent-snapshot guarantee.
Preserve initialization payloads from discarded snapshots before later uses;
current pending uploads are transferred once, not resupplied automatically.
Do not change this behavior or add SSC versioning during this refactor.
The public mutable set0 input is caller-synchronized; an internal mutex is not
a promise that external mutations can race safely with takeSnapshot().

Retain set 0 as the common binding contract and set 1 as kernel-private
bindings. Centralize shared shader layout and semantics for effect authors.
Keep current shared lighting/exposure conventions and visual behavior for the
initial migration. Moving tone mapping to a separate effect is deferred;
define image kernels' input/output color semantics explicitly in the meantime.

Typed CPU parameters are packed into shader ABI layouts by the kernel; do not
assume arbitrary C++ structs can be memcpy'd into uniforms. Immediate values
can lower to push constants or uniform data according to backend capabilities.
External uniform-buffer inputs, when needed, use a typed, documented ABI view
with validated range, alignment, device, and producer ordering. No reflection
or runtime string binding is required in the normal invocation path.
SSC's single-version rule does not permit overwriting private constants used
by earlier recorded invocations: retain copied immediate data or distinct
private buffer ranges until their uses are complete.

### Image algorithms and portability

Blur initially uses horizontal then vertical passes/dispatches, with defined
sigma/radius, edge handling, dimensions, format, and aliasing rules. Scratch
belongs to the recording lifetime. Reject unsupported aliasing explicitly.

Mipmap generation reads level N and writes N+1, with each next step dependent
on the preceding write. Explicitly define base/last mip, supported layers,
odd-dimension filtering, and the no-work case. Restrict the first implementation
to color filtering; depth reduction and normal-map renormalization are separate
semantics. Preserve base mip data. Define linear/sRGB conversion consistently.
No kernel resizes a caller texture or adds absent mip storage: the caller must
provide the destination levels and supported usages. Specify whether alpha is
filtered as straight or premultiplied data, and keep raster/compute variants
equivalent under that documented convention. Zero-radius blur and an empty mip
range need explicit copy/no-work semantics rather than accidental behavior.

Raster variants establish a path for WebGL 2 / GLES 3.0-class capabilities;
compute variants target capable native APIs and WebGPU. Higher-level selection
checks actual formats, texture usages, limits, and features, not OS names alone.
Shader portability includes WGSL/GLSL ES output and shared ABI validation;
the current Vulkan shader binaries alone do not establish web compatibility.
Native backend implementation and a full shader-toolchain replacement are
outside scope; record concrete gaps instead of claiming untested support.

Check sampleable, filterable, renderable, and storage-writable support
separately. Do not require subgroups, float atomics, cross-workgroup barriers,
native push constants, or large workgroup memory for baseline implementations.
Subresource feedback restrictions can require scratch/copy strategies on some
backends; logical mip views alone do not prove legality on every API.
Do not claim all kernels support every arbitrary buffer/texture feature on
every platform. Each kernel has explicit capability requirements.
